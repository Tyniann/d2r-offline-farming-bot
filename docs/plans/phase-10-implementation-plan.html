D2R Offline Farming Bot · Phase 10

Erweiterbare Run-Definitionen und Mephisto

Phase 10 löst den vollständigen Farming-Lifecycle aus der Countess-spezifischen State-Machine, migriert Countess ohne Verhaltensverlust auf einen gemeinsamen typisierten Run-Vertrag und integriert Act-3-Mephisto als zweites echtes Farmziel. Der erste Mephisto-Scope ist fest an MrBones, Nightmare, Durance-of-Hate-Level-2-Waypoint und eine gültige aufgezeichnete Route gebunden. Automatische Kartenerkundung bleibt ausgeschlossen.

Architekturbeweis

Countess und Mephisto verwenden denselben Session-, Waypoint-, Route-, Encounter-, Loot-, Portal- und Town-Lifecycle. Zielspezifisch bleiben nur Daten und nachweislich notwendige Strategien.

Zweiter Run

Act 1 → Durance Level 2 → aufgezeichnete Route → Mephisto → Loot → Kurast-Docks → Act-1-Hub → Save & Exit.

Loot-Test

Makellose/perfekte Gems bleiben Stash-Loot. Exceptional-/Elite-Set- und Unique-Items werden aufgenommen, bei Cain identifiziert und bei Akara verkauft.

GUI-Vorbereitung

Eine read-only CLI-/JSON-Abfrage liefert Run-Metadaten und Verfügbarkeit. Die lokale API und GUI-Anbindung folgen erst in Phase 11.

4. Gemeinsamer Run-Vertrag

type RunDefinition struct {
    ID                 RunID
    DisplayName        string
    EntryArea          world.AreaID
    RouteTerminalArea  world.AreaID
    WaypointTarget     pathing.WaypointTargetID
    Boss               BossDescriptor
    BossEngageSequence []EncounterAction
    ReturnOrigin       town.OriginAct
    RequiredCaps       []RunCapability
}

type RunConfig struct {
    RouteID string
    Combat  CombatConfig
    Loot    RunLootConfig
}

type RunAvailability struct {
    RunID       RunID
    DisplayName string
    Status      string // available | unavailable | runtime_validation_required
    Reasons     []string
    Route       RouteAvailability
}

Die endgültigen Go-Namen werden in 10.0 festgeschrieben. Wichtig ist die Trennung: Produktidentität und feste Fähigkeiten kommen aus der Registry; operatorabhängige Route, Profil und Tuning kommen aus Config; Live-Layout und UI werden erst durch Preflight beziehungsweise den zuständigen Executor bestätigt.

Spätere Farm-Reihenfolge: Eine GUI soll später beispielsweise mephisto → countess → baal zusammenstellen. Phase 10 implementiert dafür stabile IDs, Metadaten und Verfügbarkeitsgründe. Die Session führt weiterhin genau eine ausgewählte Definition aus; der spätere Scheduler orchestriert mehrere Sessions, ohne Run-Interna zu kennen.

5. Gemeinsame State-Machine

resolve_definition
→ precheck
→ town_ready_profile
→ acquire_act1_waypoint
→ select_run_waypoint
→ wait_entry_area
→ play_bound_route
→ acquire_boss
→ boss_engage_action[0..n]
→ engage_boss
→ confirm_kill
→ scan_and_pick_loot
→ cast_and_enter_town_portal
→ wait_origin_town
→ normalize_to_act1_hub
→ stash_and_services
→ reach_act1_waypoint
→ complete
  • Jeder Zustand besitzt erlaubte Vorgänger, zulässige World-Areas, Input-/Verify-Budget, Timeout und stabilen terminalen Reason-Code.
  • Persistenter Zustand über Ticks: Definition, Route-/Layout-Bindung, gepinnte Boss-UnitID, Encounter-Aktionsindex, Loot-Skips, Town-Plan und Telemetrie-Recorder.
  • Reset verwirft alle Pins, Once-/Settle-Zustände, laufende Player/Executor und Recorder-Bindungen. Es darf kein verzögerter Input in den nächsten Run gelangen.
  • Countess und Mephisto verwenden dieselbe Transition-Tabelle. Unterschiedliche Aktionsanzahl, Areas und IDs werden ausschließlich aus der Definition gelesen.
  • Loading-/inkonsistente Snapshots dürfen innerhalb der explizit erlaubten Übergangszustände warten; in jedem anderen Zustand gilt fail-closed.

Route, Combat, Pickup- und Sell-Policy werden ausschließlich über die ausgewählte Run-ID aufgelöst, während Loot-Engine und Inventory-Lock global bleiben. 10.2

Gemeinsame Run-Pipeline und vollständige Countess-Migration — abgeschlossen am 13. Juli 2026

Die monolithische Countess-State-Machine in eine datengetriebene, aber typisierte Pipeline überführen. Waypoint-Reise, Routen-Playback, Boss-Pinning, Encounter-Aktionssequenz, Combat, Loot, Portal, Town und Abschluss werden gemeinsame Steps. Countess liefert ausschließlich Definition und Config. Die isolierten Phasen werden direkt generisch benannt; alte Countess-Phasennamen oder CLI-Aliase bleiben nicht bestehen.

  • Ein Encounter-Aktionsindex erlaubt Countess genau eine Hook-Aktion und später Mephisto zwei.
  • Boss-Pin, Route-Player, Profile-Executor, Loot-Executor und Town-Executor werden an einer zentralen Reset-Barriere geleert.
  • Alte Countess-Step-Switches, doppelte Prechecks und unbenutzte Adapter unmittelbar entfernen; kein toter Fallback-Code.
  • Telemetry behält stabile Run-/Step-/Outcome-Felder und ergänzt Definition-ID sowie Aktionsindex.

Umgesetzt: internal/tasks/run_pipeline.go führt Full Runs und isolierte Ausschnitte ohne Run-ID-Factory-Switch aus. Entry-/Terminal-Area, Waypoint-Ziel, Boss, Suchfallback, Encounter-Sequenz und Rückkehrakt kommen aus RunDefinition; Route, Combat und Loot-Policies aus dem ID-basierten RunConfig. Die generischen CLI-Phasen heißen ausschließlich travel-entry, play-route, boss, loot-and-return, stash-personal und town-ready. Alte CountessPhase*-, countessRun- und countessStep*-Namen sowie die alten CLI-Werte wurden aus Code, Tests und Dokumentation entfernt.

Reset und Telemetrie: Eine idempotente zentrale Run-Generation-Barriere leert Waypoint, Portal, Town-Walk, Stash, Navigator, Route-Player, Combat, Loot, Town, Profil, Boss-Pin und Encounter-Index genau einmal. Pipeline-Transitionen persistieren definition_id, step und outcome; Encounter-Start/-Abschluss ergänzt action_index. Ein Emit-Fehler blockiert den folgenden Profil- oder Combat-Input und endet fail-closed mit telemetry_failed.

Abschnittsgrenze: Der produktive Black-Marsh-UI-Klick bleibt bis 10.7 hinter einem definitionsneutralen Run-Waypoint-Adapter. Damit kennt die gemeinsame Pipeline keine Countess-UI-Aktion, ohne die registrierte Mehrziel-Auswahl, Act-Tabs oder neue Koordinaten vorwegzunehmen. Der frühere produktive Explorer-/Cellar-Fallback ist aus der Pipeline entfernt.

Gate 10.2 erfüllt: Die semantisch unveränderte Characterization-Suite läuft direkt gegen die generisch benannte Pipeline. Transition-, Timeout-, zentrale Reset-, Stop-, Pause-, Encounter-Index- und Telemetriefehler-Tests sind grün und beweisen, dass nach fehlgeschlagener Telemetrie kein Folgeinput entsteht und kein Generation-State übertragen wird. go test ./..., go build ./cmd/d2rbot, die Suche nach allen entfernten Namen/Fallback-Steps und git diff --check sind erfolgreich. Kein manueller Test.

10.3

Generischer Session-Preflight und read-only Run-Verfügbarkeit — abgeschlossen am 13. Juli 2026

ResolveSessionPlan wird von Countess entkoppelt und fragt ausschließlich Registry, ausgewählte Config, Profil, Route Registry und Town-Capabilities ab. Die neue read-only CLI-Ausgabe --runs-inspect listet JSON-stabil alle Run-Metadaten und deren Status für Character, Difficulty und Game Identity.

  • available: statische Definition, Config, Profil und passend gebundener Route-Kandidat sind vorhanden und der übergebene Live-Fingerprint passt.
  • runtime_validation_required: Vorbedingungen passen, der exakte Zielgebiets-Fingerprint kann aber erst nach Ankunft validiert werden.
  • unavailable: mindestens ein stabiler Sperrgrund wie route_missing, route_binding_mismatch, profile_class_mismatch, waypoint_target_unsupported oder town_egress_missing.
  • Die Abfrage registriert keine Hotkeys, sendet keinen Input und startet keine Session.

Umgesetzt: ResolveRunAvailabilities bewertet alle Registry-Definitionen in stabiler ID-Reihenfolge gegen den expliziten read-only Kontext aus Character, Class, Difficulty, Game-Version, optionalem Map-Seed und Layout-Fingerprint. Reasons werden dedupliziert und lexikografisch sortiert. ResolveRunsInspectReport leitet ohne Prozess-Attach den statischen Session-Kontext ab; leere Live-Felder werden nicht geraten.

Lokaler Befund: Die gebundene Countess-Route black-marsh-cellar5-nightmare-mrbones ist für MrBones/Nightmare/3.2.92777 statisch passend und liefert ohne Zielgebiets-Fingerprint korrekt runtime_validation_required; mit Seed 466817790 und passendem Fingerprint liefert derselbe Resolver available. Mephisto bleibt deterministisch mit route_missing und waypoint_target_unsupported gesperrt.

Session-Entkopplung: ResolveSessionPlan verwendet denselben Availability-Resolver und besitzt weder Countess-/Mephisto-Sondergate noch duplizierte Route-Bindungsprüfung. unavailable stoppt vor Runtime-Erzeugung; runtime_validation_required bleibt zulässig, weil Route Playback den Live-Fingerprint vor Routeninput autoritativ prüft.

Gate 10.3 erfüllt: Golden-/JSON-, Binding-, Profile-Class-, Town-Egress-, CLI-Konflikt- und Session-Blockadetests beweisen deterministische Reihenfolge und stabile Reason-Codes. go test ./..., go build ./cmd/d2rbot, lokales --runs-inspect, lokales --session-inspect, Sonderpreflight-Suche und git diff --check sind erfolgreich. Kein manueller Inputtest.

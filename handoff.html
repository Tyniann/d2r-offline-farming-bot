D2R Offline Farming Bot

Handoff-Dokument für ein privates Offline-only Singleplayer-Projekt: Ziel ist die technische Automatisierung von Diablo II: Resurrected Farming-Runs, beginnend mit Countess Runs und später optional Mephisto, Cow Level und Baal.

Offline only Singleplayer Memory Bot Core Go 1.26 Countess MVP Stand: Phase 9 abgeschlossen
Go Core

Umgesetzter Stack: Go für Memory Reader, World Model, Input Controller und Task Runner; YAML-Konfiguration, slog-Logging. Später optional TypeScript/React für Dashboard, Pickit-Editor und Run-Auswertung.

1. Projektziel

Das Projekt soll eine externe Software entwickeln, die einen Offline-Diablo-Charakter durch wiederholbare Farming-Runs fuehren kann. Der Fokus liegt nicht auf dem Veraendern eines Spielstands, sondern auf dem Bau einer Automatisierung, die Spielzustand erkennt, Entscheidungen trifft und Eingaben ausfuehrt.

Das Zielbild ist ein Bot, der Run-Ziele als Tasks abarbeitet: Town-Vorbereitung, Waypoint-Nutzung, Navigation, Kampf, Loot-Auswertung, Rueckkehr, Stash/Repair/Reset und Logging.

2. Recherche-Kernaussagen

D2R-Modding

D2R-Modding ist im Wesentlichen datengetrieben. Uebliche Wege sind -mod, -txt, extrahierte CASC-Daten und Dateien unter data/global/excel.

Bot-Logik

Eine echte Mod API fuer autonome Bot-Logik oder Charaktersteuerung wurde nicht gefunden. Fuer echte Runs braucht es eine externe Automationsschicht.

Beste Passung

Ein Memory Bot passt am besten zum Ziel, weil er Spielzustand, Map, Entities und Items direkter erfassen kann als ein reiner Pixelbot.

Ansatz Geeignet fuer Charaktersteuerung Einschaetzung
Daten-Mod Drop-Tables, Skills, Items, Monsterwerte, QoL, Testumgebung Nein Nuetzlich als Support-Layer, aber kein Bot.
Pixelbot Prototyping ueber Screenshots, OCR, Template Matching Ja Einfacher Start, aber fragiler bei UI, Aufloesung und Sonderfaellen.
Memory Bot State-aware Farming, Map/Entity/Item-Daten, robustere Navigation Ja Beste technische Passung, aber hoechster Aufwand.
Savegame/Simulator Drop-Forschung, Tests, Reward-Simulation Nein Gute Alternative fuer Analyse, aber nicht fuer Gameplay-Automation.
Read-only QoL Tool Run-Tracking, Loot-OCR, Stash-Backups, Drop-Statistiken Nein Sinnvoller erster Baustein und Debug-Hilfe.

3. Empfohlener Tech-Stack

Schicht Empfehlung Warum
Bot Core Go Guter Kompromiss aus Produktivitaet, Systemnaehe, Binary-Handling, Nebenlaeufigkeit und vorhandener D2/D2R-Projektnaehe.
Konfiguration YAML oder JSON Gut lesbar fuer Build, Skills, Pickit-Regeln, Hotkeys und Run-Parameter.
Logging JSONL plus menschenlesbare Logs Ermoeglicht Debugging, Run-Auswertung und spaetere Visualisierung.
Debug UI Lokale Web UI oder CLI zuerst Schnelle Iteration; UI kann spaeter wachsen.
Spaetere UI TypeScript/React oder Electron optional Gut fuer Dashboard, Kartenansicht, Pickit-Editor und Statistiken, aber nicht ideal als Memory-Core.
Warum nicht JavaScript/TypeScript als Core?

Node.js kann Windows-APIs ueber FFI/native Addons erreichen, aber dadurch entsteht zusaetzliche Interop-Komplexitaet. Fuer Prozesszugriff, binaere Strukturen, Pointer-Ketten, Polling und Eingabe- Simulation ist Go als Core naheliegender. TypeScript bleibt stark fuer Oberflaechen, Tools und Reports.

4. Zielarchitektur

loot Item-Erkennung, Pickit-Regeln, Inventory/Stash-Handling. Kann er Runen erkennen und nur gewuenschte Items aufnehmen?
safety Stop-Hotkey, Pause, Stuck Detection, Low-HP-Verhalten, Death-Recovery. Kann der Nutzer jederzeit stoppen und kann der Bot aus Fehlern aussteigen?
telemetry Logs, Screenshots, Run-Dauer, Drops, Fehlergruende, Debug-Dumps. Kann man nach jedem Fehllauf nachvollziehen, warum er gescheitert ist?
api (ab Phase 11) Lokaler, stabiler Steuer- und Live-Statusvertrag zwischen Go-Core und Bedienoberfläche. Kann die GUI Sessions bedienen, ohne interne Pakete, YAML oder Logs direkt zu manipulieren?

5. MVP-Plan und Umsetzungsstand

Phase 0

Projekt-Skelett und Dokumentation — abgeschlossen

Repository/Ordnerstruktur, Handoff-Dokument, Grundentscheidungen, Beispiel-Konfigurationen.

Read-only State Probe — abgeschlossen

Prozess-Erkennung, Memory Reader, Snapshot mit HP/Mana, Area, Spielerposition. Patch-sensitive Offsets werden per Signature-Scan (d2go-Referenz) zur Laufzeit ermittelt und gecacht; YAML-Overrides über configs/offsets.local.yaml.

Phase 2

World Model und Kartenverständnis — abgeschlossen

Area-Katalog und Positionsdaten im internen Modell. Der Bot erkennt, ob er in Town, Black Marsh, Forgotten Tower oder Tower Cellar ist. Validiert für die Countess-Route.

Phase 3

Input Controller — abgeschlossen

Fenster-Binding, Tastatur/Maus-Primitiven über SendInput, Pause/Stop-Hotkeys, Aktions-Logging, CLI-Input-Test. Skill-, Town-Portal- und Belt-Belegung kommen aus expliziten YAML-Bindings (input.bindings) — der frühere Versuch, Tastenkürzel aus dem Speicher zu lesen, wurde verworfen.

Phase 4

Countess MVP ohne Pickit — abgeschlossen

Start in Town, Waypoint zu Black Marsh, Tower finden, Level 1–5 traversieren, Countess-Raum finden, Kill-Versuch, Run beenden. Noch keine perfekte Loot-Logik.

  • 4.1 Task-Runner-Framework — Run-State-Machine, Step-Timeouts, Countess-Stub. Abgeschlossen.
  • 4.2 World-Erweiterung — Unit-Enumeration (Objects, Entrances, Monster inkl. UnitID), GamePhase, Entity-Logging. Abgeschlossen.
  • 4.3 Pathing-Grundlagen — Teleport-Navigation, Bearing-Explore und Hover-bestätigte Entity-Klicks.
  • 4.4–4.7 Countess-Run — Travel-Steps, best-effort Tower-Traversierung, Countess-Kill und vollständige Orchestrierung.
Phase 5

Loot und Recovery — abgeschlossen

Ground-Items, Pickit, geschützter Pickup, Inventory-Full-Recovery, Personal Stash, Identifikationsstrategie und fail-closed JSONL-Telemetrie pro Run.

Phase 6

Generische Routenaufzeichnung und Wiedergabe — abgeschlossen

Recorder, Routenmodell, Registry, Validator und Player werden run-unabhängig gebaut und später auch von Mephisto-, Cow-, Baal- oder benutzerdefinierten Runs verwendet. Countess ist der erste vollständig integrierte Use Case: Der Spieler zeichnet Black Marsh → Forgotten Tower → Tower Cellar Level 5 einmal auf und der Bot spielt die Route Memory-verifiziert wieder ab.

Stabile Route-IDs und GUI-taugliche Metadaten bereiten die spätere Verwaltung, Auswahl und Zuordnung aufgezeichneter Routen zu Run-Definitionen vor.

  • 6.0 Route Contract v1 — generisches Schema, stabile IDs, Registry-Metadaten, Identity-Bindung, Sampling, Fehlerklassen und CLI-Vertrag. Abgeschlossen.
  • 6.1a–d Game Identity und Layout-Sicherheit — abgeschlossen. Name/Klasse werden über drei Snapshots stabilisiert; Hell und Nightmare wurden kontrolliert gestartet; Nightmare reproduzierte denselben Layout-Fingerprint über zwei neue Spiele und unterschied sich von Hell. Kein persistenter Auswahl-Cache.
  • 6.2 Routenmodell und Registry — Route Contract v1, YAML-Storage, Validator, Duplikatsperre, Compatibility-Precheck und read-only CLI abgeschlossen.
  • 6.3 Read-only Recorder — abgeschlossen. Die Nightmare-Route für `MrBones` wurde mit sechs bestätigten Segmenten von Black Marsh bis Cellar 5 aufgezeichnet und erneut validiert.
  • 6.4 Segment-Playback — abgeschlossen. Alle sechs Nightmare-Segmente wurden isoliert bis zum bestätigten Area-Wechsel wiedergegeben; falsche Start-Area blockiert vor Input.
  • 6.5 Memory-verifizierte Transitions — abgeschlossen. Semantische Entrance-Auswahl, Unit-Pinning, begrenzte lokale Recovery und Click-Settle verhindern falsche oder wiederholte Klicks.
  • 6.6 Vollständiges Playback — abgeschlossen. Zehn vollständige Wiedergaben im stabilen Nightmare-Layout (neun direkte Replays, ein Countess-Adapter-Lauf) erreichten Cellar 5; JSONL bestätigt jeweils sechs Segmente. Begrenzte Drift-Recovery nutzt nur bestätigte Routenpunkte; drei Driftfehler brachen fail-closed ab.
  • 6.7 Countess-Integration — abgeschlossen. Stabile Route-ID, dünner App-Adapter und Task-Schritt ersetzen Explorer im regulären Erfolgspfad; die Live-Abnahme erreichte über sechs bestätigte Segmente Cellar 5.

Detailplan und Abnahme: Phase-6-Umsetzungsplan.

Phase 7

Autonomer Multi-Run- und Game-Lifecycle — abgeschlossen

Der Bot verlässt ein abgeschlossenes Offline-Spiel kontrolliert, startet das nächste Spiel mit verifiziertem Charakter und Schwierigkeitsgrad, erzeugt frischen Run-Zustand und führt eine endliche Session mit Recovery-Budgets und korrelierter JSONL-Telemetrie aus.

  • Memory- und Screen-gated Charakterauswahl, Difficulty-Auswahl sowie Save & Exit.
  • Frische Game-/Run-IDs, vollständige Reset-Barriere, Cooldown sowie Run-, Zeit- und Restart-Limits.
  • Hard-Stuck-Abbruch und exakte, fail-closed Recovery-Klassifikation.
  • Terminaler Keller-5-Routenabschnitt bis in den Countess-Raum.
  • Drei autonome Nightmare-Countess-Zyklen einschließlich Kill, Loot, Town Portal, Stash und Save & Exit erfolgreich.

5a. Verbindliche Roadmap ab Phase 8

Diese Roadmap ist die zentrale Reihenfolge für die weitere Produktentwicklung. Detailpläne werden pro Phase separat ausgearbeitet; der Ideen-Backlog bleibt unverbindlich.

Phase 8

Generische Character- und Encounter-Profile — abgeschlossen

Ziel: Klassen- und kampfspezifisches Verhalten ergänzen, ohne Necromancer-Sonderlogik in einzelne Runs einzubauen.

Umfang:

  • Generische Hooks wie town_ready, boss_engage und später weitere klar begrenzte Encounter-Ereignisse.
  • Konfigurierbare Aktionen mit Zieltyp self, boss oder World-Position sowie once_per_game/once_per_encounter.
  • Necromancer-Profil: Bone Armor einmal in Town und Bone Prison einmal auf die bestätigte Boss-Unit.
  • Profilkonfigurierbare Resource Policy für Healing, Mana und Rejuvenation; höchstens eine bestätigte Potion-Aktion pro Tick.
  • Klassen-, Binding-, Reset-, Timeout- und Telemetrie-Gates als wiederverwendbarer Vertrag für Paladin und Sorceress.

Abnahme: Drei gezielte manuelle Live-Durchläufe insgesamt: Bone Armor isoliert, kontrolliert niedriges Mana plus Bone Prison isoliert und ein vollständiger Countess-E2E-Zyklus; falsche Klasse, fehlendes Binding oder ungeeigneter Belt-Slot blockiert den betreffenden Input.

Detailplan: Phase-8-Umsetzungsplan.

Phase 9

Aktbewusste Town Services und Run-Vorbereitung — abgeschlossen

Ergebnis: Vor einem Run werden nur tatsächlich notwendige Stadtaktionen sicher ausgeführt; Planung, Navigation, Interaktion und Verifikation bleiben getrennte fail-closed Gates.

Architektur:

  • Rogue Encampment ist der zentrale Stash- und Service-Hub mit dem einzigen vollständigen Town-Graphen.
  • Ein Service-Registry-Modell ordnet Bedarfe wie Potions, Scrolls, Identify, Sell, Repair und später Mercenary-Revive einem lokalen Anbieter zu.
  • Andere Akte erhalten pro unterstütztem Farmziel nur einen minimalen Egress von Portal-/Startanker zum lokalen Waypoint; Stash- und NPC-Graphen werden dort nicht dupliziert.
  • Die Route bringt den Charakter nur in Interaktionsnähe; ein NPC-Klick benötigt nach Möglichkeit Memory-Entity und Hover-bestätigte UnitID sowie einen bestätigten Shop-/Dialogzustand.
  • Nach Fremdakt-Egress wechselt der Bot über den Waypoint nach Act 1, verstaut Loot zentral und erledigt dort alle benötigten Dienste.
  • Nach Abschluss endet Town Preparation am Act-1-Waypoint und übergibt von dort direkt an das Ziel des nächsten Runs.
  • Der endliche Waypoint-Transfervertrag bestätigt Quellakt, Zielgebiet und Ankunft vor einem weiteren Input; Phase 9 registriert bewusst nur Act 3 → Rogue Encampment und Rogue Encampment → Black Marsh.

Bedarfsmodell: Belt- und Inventarbestand, kaufbare HP-/Mana-Potion-Zielbelegung, Town-Portal-/Identify-Vorrat, nicht identifizierte Items, explizite Vendor-Kandidaten, Reparaturzustand und verfügbare Goldkosten werden zuerst read-only bewertet. Rejuvenation ist ausdrücklich kein Town-Kaufbedarf; vorhandene Bestände werden geschützt und Nachschub kommt vorerst nur über Pickit-Loot.

Restock-Strategie: Belt-Spalten stammen ausschließlich aus dem aktiven Combat-Profil. Erst beim Unterschreiten einer konfigurierten Mindestmenge entsteht ein Restock-Bedarf. Ein vollständig typisierter Belt erlaubt genau einen Shift+RMB-Sammelkauf; unzugewiesene Belt-Spalten erzwingen einen begrenzten Einzelkaufpfad. Nicht verlässlich lesbare Tome-Zähler bleiben ein dokumentierter unavailable_skip.

Sicherheitsgrenzen: Unbekannter Akt, fehlendes Town-Profil, unbekannter Startanker, fehlende Route, nicht bestätigter NPC, unbestätigte Shop-UI oder nicht unterstützter Aktwechsel enden fail-closed ohne Blindlauf oder Blindklick.

Reihenfolge: Hub-/Egress-Vertrag → Herkunftserkennung → Hub Planner → Act-1-Servicegraph → Waypoint-Hubtransfer → zentraler Stash → Einkaufen → Identifizieren/Verkaufen/Reparieren → Handoff zum nächsten Run.

Umgesetzter Scope: Rogue Encampment ist der einzige vollständige Service-Hub. Nord-, Ost-, Süd- und West-Preset besitzen jeweils einen vollständigen layoutgebundenen Kantensatz; Character und Difficulty sind keine Town-Route-Bindings. Weitere Farmziele ergänzen später nur Ziel-Waypoints und minimale Town-Egress-Routen.

Abnahme: Alle drei manuellen Gates sind erfüllt. Der finale autonome Nightmare-Lauf betrat das Portal nach dem 500-ms-Aktivierungsgate, verstaute acht Items, erzeugte ausschließlich den notwendigen Akara-Bedarf, erhöhte Mana mit genau einer Bulk-Aktion von 2 auf 12, bestätigte Shop-Close und Waypoint-Handoff und endete mit Save & Exit sowie runs_successful=1/1. Negative Tests decken unbekannte Herkunft, fehlende Egress-/Layout-Routen, unbestätigte UI, unzureichendes Gold sowie endliche Input-/Verify-Budgets ab.

Detailplan: Phase-9-Umsetzungsplan.

Phase 10

Erweiterbare Run-Definitionen und Mephisto — als Nächstes

Ziel: Mit Act-3-Mephisto als zweitem echten Farmziel beweisen, dass Session, Profile, Route, Loot, Stash und Recovery nicht Countess-spezifisch sind.

Festgelegter Scope: Eine typisierte, GUI-neutrale Run Registry ersetzt Countess-spezifische Config-, Preflight- und State-Machine-Kopplung. Pro Session wird genau ein Run ausgewählt. Der erste Mephisto-Run gilt für MrBones auf Nightmare, verlangt eine passende aufgezeichnete Durance-Route, castet zweimal Bone Prison vor Bone Spear und kehrt über Kurast-Docks sowie den Act-3-Egress in den Act-1-Hub zurück. Automatische Kartenerkundung und Söldnerlogik bleiben ausgeschlossen.

Loot-Test: Makellose und perfekte Gems bleiben Stash-Loot. Exceptional-/Elite-Set- und Unique-Items werden aufgenommen, bei Cain identifiziert und anschließend bei Akara verkauft. Verbleibender Bodenloot darf bei vollem Inventar aufgegeben werden.

GUI-Vorbereitung: Phase 10 liefert eine read-only CLI-/JSON-Abfrage für Run-Metadaten und Routenverfügbarkeit. Die lokale Core-API, GUI-Anbindung und frei zusammenstellbare Farm-Reihenfolgen wie Mephisto → Countess → Baal fehlen weiterhin und werden erst ab Phase 11 umgesetzt.

Abnahme: Countess und Mephisto sind über denselben Lifecycle auswählbar und bestehen jeweils einen vollständigen autonomen E2E-Zyklus ohne duplizierte Session- oder Input-Logik.

Detailplan: Phase-10-Umsetzungsplan.

Phase 11

Ziel: Eine lokale Bedienoberfläche steuert den Go-Core über einen stabilen Vertrag, statt YAML, Logs oder interne Pakete direkt zu manipulieren.

Ziel: Den lokalen Bot reproduzierbar installieren, konfigurieren, aktualisieren und sicher betreiben.

5b. Koordinaten und Klick-Präzision — die Koolo-Methode

Für Bewegung und Entity-Klicks braucht der Bot eine Abbildung von Weltkoordinaten (Tiles) auf Bildschirmpixel. Ein früherer Ansatz sah vor, dafür die Kamera-/Viewport-Position per manuellem Reverse Engineering aus dem D2R-Speicher zu lesen. Dieser Ansatz ist verworfen: Keine öffentliche Referenz (Koolo, d2go, MapAssist) liest eine Kamera aus dem Speicher, und manuelles RE pro Spiel-Patch ist für dieses Projekt nicht leistbar.

Stattdessen übernimmt das Projekt das bewährte Modell des Go-Bots Koolo:

  • Relative Projektion: Der Spieler ist immer (nahezu) das Zentrum des spielbaren Bereichs. Ziel-Pixel ergeben sich aus der isometrischen Formel screenX = (dx − dy) · 19.8 + centerX, screenY = (dx + dy) · 9.9 + centerY mit dx/dy = Ziel − Spieler in Tiles. Keine Kamera-Daten nötig.
  • Hover-Feedback-Loop: Präzision kommt nicht aus der Projektion, sondern aus einem geschlossenen Kreislauf: Maus zum projizierten Punkt bewegen, dann die Hover-Daten des Spiels aus dem Speicher lesen ({IsHovered, UnitType, UnitID}). Erst wenn die anvisierte Unit bestätigt unter dem Cursor liegt, wird geklickt. Trifft die Projektion nicht sofort, sucht eine Spiral-Bewegung um den Startpunkt. Kein Klick ohne Hover-Bestätigung.
  • Hover-Offset per Signature-Scan: Der Speicher-Offset für die Hover-Daten wird — wie bereits UnitTable und UI-Gate — automatisch über ein d2go-Byte-Pattern gefunden, nicht durch manuelle Speicheranalyse.
  • Feste Fenstergröße: Empfohlen ist 1280×720 im Fenstermodus (Koolo-Kalibrierung der Projektionskonstanten); Abweichungen erzeugen eine Warnung.

6. Run-Ziele und erwartete Schwierigkeit

Run Eignung Warum
Countess Gut fuer MVP Kurzes Ziel, relevante Runen-Drops, ueberschaubarer Bosskampf, aber zufaellige Tower-Layouts.
Mephisto Gut als zweiter Boss Durance-Pathing ist schwieriger, aber der Bosskampf ist relativ klar und etabliert.
Cow Level Mittel Portal-Setup, grosse Flaechen, Herding und Loot-Menge machen die State-Machine komplexer.
Baal Spaetes Ziel Waves, Immunitaeten, Throne-Clearing, Death-Recovery und lange Runs erhoehen die Fehlerquote.

7. Ordnerstruktur und geplante Erweiterungen

Die vorhandenen Paketgrenzen bleiben bestehen. Neue Ordner werden erst in der jeweils genannten Phase angelegt; insbesondere wird der funktionierende Phase-7-Session-Code nicht vorsorglich verschoben.

Pfad Zweck
/cmd/d2rbot Main executable fuer den Bot.
/internal/app Runtime-Wiring, Lifecycle und Adapter zwischen den fachlichen Paketen.
/internal/config YAML laden, Defaults anwenden und Operator-Konfiguration fail-closed validieren.
/internal/process Prozesssuche, Handles, Lifecycle.
/internal/memory Memory Reader, Snapshots, binaere Strukturen.
/internal/world Spielzustand, Areas, Entities, Items, Objekte.
/internal/pathing Teleport-/Navigationslogik.
/internal/input Keyboard/Mouse-Aktionen und Hotkeys.
/internal/tasks Run-State-Machines.
/internal/profile (Phase 8) Generische Character-/Encounter-Profile, Hook-Vertrag, Once-/Reset-Semantik und Resource Policy. Keine Unterordner pro Charakterklasse.
/internal/town (Phase 9) Town-Profile pro Akt, Service Registry, Bedarfsmodell, Anker-Routengraph und endliche Town-Preparation. Bewegung selbst bleibt in pathing.
/internal/loot Pickit-Regeln, Item-Filter, Inventory/Stash.
/internal/telemetry Run-/Session-JSONL, stabile Ereignisse, Korrelation und spätere Historienbasis.
/internal/api (Phase 11) Lokale Core-API und Live-Events. Alle mutierenden Befehle verwenden bestehende Safety-Gates.
/web (Phase 11) TypeScript-/React-Oberfläche; kein direkter Zugriff auf Memory, Input, Tasks oder lokale YAML-Dateien.
/configs YAML/JSON für Builds, Runs, Hotkeys und Pickit. Permanente Town-Assets liegen unter routes/town/<act>/, invalidierbare Farming-Sätze unter routes/farming/<character>/<difficulty>/.
/docs Recherche, Architekturentscheidungen, Debug-Notizen.
Abhängigkeitsgrenzen: config lädt Definitionen; profile und town treffen fachliche Entscheidungen; app verdrahtet World und Input; input führt ausschließlich bereits autorisierte Primitive aus. Die spätere GUI kommuniziert nur über internal/api. Town-Dienste werden nicht in pathing und Klassenlogik wird nicht in einzelne Run-State-Machines eingebaut.

Snapshot-Konsistenz wird über Validitäts-Flags und Re-Reads gelöst; die Boundary process → memory → world → tasks → input ist umgesetzt; patch-sensitive Offsets kommen aus Signature-Scans mit YAML-Override; Tastenkürzel kommen aus YAML statt aus dem Speicher; World→Screen braucht keine Kamera-Daten (Koolo-Methode, Abschnitt 5a). Die globale Tower-Erkundung bleibt best-effort; Phase 6 ersetzt sie im produktiven Countess-Run durch manuelle Routenaufzeichnung und deterministische, Memory-verifizierte Wiedergabe. Route Contract v1 trennt Navigation von Run-Definitionen, verwendet stabile Route-IDs und bindet fail-closed an Memory-bestätigten Charakter, Spielversion und einen reproduzierten Layout-Fingerprint. Der in 6.1a gelesene Seed ist kein Identitätsschlüssel. Difficulty wird durch den Bot im Offline-Menü kontrolliert gewählt, gibt Playback aber nicht frei; dafür ist ausschließlich der Layout-Precheck zuständig.

D2R Offline Farming Bot · Phase 13

Pickit-Profile verständlich erstellen, prüfen und sicher anwenden

Phase 13 ersetzt technische Einzeldateien durch kleine, wiederverwendbare Pickit-Profile mit geführter Itemsuche, zwei eindeutigen Aktionen und einer nachvollziehbaren Entscheidungsvorschau. Der vorhandene Loot-Core bleibt die Ausführungsautorität. Patchgenaue Set-/Unique-Identitäten werden aus den selbst extrahierten D2R-Excel-Dateien generiert; eine fremde Itemdatenbank oder ein vollständiger NIP-Interpreter entstehen nicht.

KISS + YAGNICASC als DatenquelleTal Rasha auswählbarEthereal + Base ItemYAML Source of TruthNIP-Subset ImportFail-closed

Items statt Codes

Der Benutzer sucht nach Sets, einzelnen Set-/Unique-Items, Basisitems, Gems, Runen oder Keys und erhält daraus transparente Regeln.

Wiederverwendbare Profile

Globale Profile wie „Gems“, „Tal Rasha“ oder „Keys“ werden pro Charakter und Run in einer eindeutigen Reihenfolge zugeordnet.

Erklärbare Entscheidung

Vor dem Speichern zeigt eine deterministische Vorschau jede geprüfte Regel, das erste Match und die resultierende Aktion.

Sicherer Runtime-Wechsel

Ein laufender Run behält seinen unveränderlichen Snapshot. Gespeicherte Änderungen gelten erst an der nächsten Run-Grenze.

1. Verbindliche Produktentscheidungen

ThemaEntscheidung für Phase 13
LeitprinzipKISS und YAGNI sind verbindlich. Phase 13 erweitert nur die nachgewiesene Produktlücke: verständliche Profile, exakte Set-/Unique-Auswahl und ethereal + base item. Es entsteht weder eine allgemeine Regelsprache noch eine handgepflegte Itemdatenbank.
Datenquelleweapons.txt, armor.txt, misc.txt, itemstatcost.txt, setitems.txt, uniqueitems.txt und die englischen Werte aus item-names.json aus dem lokalen CASC-Export sind die einzige Build-Time-Datenquelle. Runtime-Code liest weder .tmp/ noch D2R-Dateien.
ItemnamenKanonische englische D2R-Namen sind in Phase 13 akzeptabel. Deutsche UI-Texte erklären Aktionen und Fehler; eine lokalisierte Itemnamendatenbank ist nicht Teil dieser Phase.
Exakte IdentitätSet-/Unique-Items dürfen beim Drop direkt anhand ihrer zweifelsfrei gelesenen D2R-Identität ausgewählt werden. Qualität, Basiscode, Identitätsart, ID und generierter Katalogeintrag müssen konsistent sein; andernfalls matcht die Regel fail-closed nicht.
PatchstabilitätProfile speichern den stabilen Excel-/String-Schlüssel, keine numerischen Set-/Unique-IDs und keinen lokalisierten Anzeigenamen. Die UI zeigt den englischen Wert aus item-names.json. Beim Laden wird der Schlüssel eindeutig gegen den für die dokumentierte D2R-Version generierten Katalog aufgelöst. Fehlende, doppelte oder widersprüchliche Einträge machen das Profil ungültig.
Ethereal„Ätherischer Thresher“ und entsprechende Kombinationen aus konkretem Basisitem plus ethereal gehören zum geführten Editor. Dafür wird ausschließlich das bereits vorhandene [flag] == ethereal verwendet.
AktionenEine Regel besitzt genau eine Aktion: Aufheben und behalten oder Aufheben, erforderlichenfalls identifizieren und verkaufen. Kein Match bedeutet ignorieren. Weitere Aktionen werden nicht vorweggenommen.
ProfileProfile sind global wiederverwendbar. Pro (character, run) wird eine nicht leere, geordnete und duplikatfreie Liste von Profil-IDs zugeordnet. Profilreihenfolge, danach Regelreihenfolge bilden eine einzige Entscheidungskette; das erste Match entscheidet.
QueueDie bestehende Farm-Queue bleibt duplikatfrei. Ein Run kann pro Spiel nur einmal vorkommen; Phase 13 führt keine Queue-Positions-spezifischen Pickit-Overrides ein.
Vollständiges SetDie Auswahl eines Sets wie „Tal Rasha’s Wrappings“ erzeugt explizit eine sichtbare Regel je Set-Item. Es bleibt keine dynamische Gruppenreferenz zurück, die sich bei einem Patch unbemerkt erweitern könnte.
EditorGeführte Suche und Schnellkategorien decken den Normalfall ab. Ein validiertes Ausdrucksfeld erschließt das bereits unterstützte NIP-Subset. Es gibt keinen visuellen Drag-and-drop-AST für beliebige Boolesche Ausdrücke.
DateiformatVersionierte YAML-Profildokumente sind die einzige persistente Autorität für Name, Regeln, Aktionen und Reihenfolge. NIP ist ausschließlich ein begrenztes Import-/Exportformat für unterstützte Ausdrücke, nicht zweite Source of Truth.
ImportPaste- und Dateiimport akzeptieren nur das dokumentierte Subset. Der Benutzer wählt vor dem Import eine Aktion. Alle aktiven Zeilen werden gemeinsam validiert; eine fehlerhafte oder nicht unterstützte Zeile verhindert die gesamte Übernahme.
Laufende SessionJeder Run verwendet einen unveränderlichen Profil-/Assignment-Snapshot mit Revision. Speichern bleibt möglich, verändert den aktuellen Run aber nie. Die Änderung gilt frühestens an der nächsten Run-Grenze; eine dann ungültige Konfiguration hält die Schleife vor weiterem Input fail-closed an.
Fehlende ZuordnungOhne gültige Pickit-Zuordnung darf ein produktiver Run nicht starten. Es gibt weder „nichts aufheben“ als stillen Fallback noch einen Legacy-Pfad über alte pickup_file/sell_file-Felder.
LöschenProfil-IDs sind unveränderlich, Anzeigenamen editierbar. Ein zugeordnetes Profil kann nicht gelöscht werden. Es gibt keine Kaskadenlöschung; „Duplizieren“ erzeugt eine neue stabile ID.

4. Persistentes Profil- und Assignment-Modell

schema_version: 1
id: tal-rasha
name: Tal Rasha Set
rules:
  - id: tal-rasha-adjudication
    action: keep
    expression: "[setitem] == \"Tal Rasha's Adjudication\""

# pickit-assignments.local.yaml
schema_version: 1
revision: 12
assignments:
  MrBones:
    countess: [gems, keys, countess-standard]
    mephisto: [tal-rasha, gems, mephisto-standard]
  • Profil-ID und Regel-ID verwenden normalisierte, case-insensitive eindeutige Slugs. Nach dem ersten Speichern ist die Profil-ID unveränderlich.
  • Regeln werden genau in YAML-Reihenfolge ausgewertet. Profile werden genau in Assignment-Reihenfolge gefaltet; es gibt keine versteckte alphabetische Sortierung.
  • Das YAML speichert die vom Benutzer bearbeitbare kanonische Expression. Der geladene AST und aufgelöste numerische Identitäten sind reine immutable Runtime-Artefakte.
  • Speichern validiert Schema, IDs, Namen, Aktion, Ausdruck, Katalogreferenzen, doppelte Regel-IDs und exakt identische widersprüchliche Bedingungen vor dem ersten Dateisystemwechsel.
  • Mutationen verwenden erwartete Revision beziehungsweise ETag. Stale Browserentwürfe erhalten einen Konflikt und überschreiben keine neuere Datei.
  • Atomischer Commit bedeutet: temporäre Datei im selben Verzeichnis, Flush/Close, Replace/Rename und anschließendes Re-Read. Scheitert ein Schritt, bleibt die vorherige gültige Version autoritativ.

5. Entscheidungs- und Runtime-Vertrag

PhaseVertrag
Run-PreflightLöst (character, run) zu einer nicht leeren Profilliste auf, lädt alle Profile, validiert Katalogrevisionen und erzeugt eine immutable EffectivePolicy mit Profil-/Regelherkunft.
Ground classifyDie geordnete Kette wird einmal ausgewertet. Sowohl keep als auch sell autorisieren den bestehenden geschützten Pickup-Pfad. Kein Match bleibt ignore.
Exakte Identitätsetitem/uniqueitem matchen nur bei passender Qualität, bekanntem Katalogeintrag, übereinstimmendem Basiscode und gültiger Raw-ID. Unbekannt, mehrdeutig oder widersprüchlich bedeutet No-Match und einen strukturierten Diagnosegrund.
KeepQualitäten, die der bestehende Vertrag als identifikationspflichtig klassifiziert, werden zuerst bei Cain identifiziert und danach mit derselben Snapshot-Regel erneut bestätigt. Nur ein erneutes keep erlaubt Stash.
SellIdentifikationspflichtige Kandidaten werden zuerst identifiziert und danach erneut gegen denselben Snapshot geprüft. Nur ein erneutes sell erlaubt Vendor-Verkauf. Ein Identitäts- oder Regelwechsel endet fail-closed und verkauft nicht blind.
MehrfachmatchNur das erste Match entscheidet. Trace und Telemetrie enthalten Profil-ID, Regel-ID, Aktion, Index und Revision; spätere Regeln werden als wegen First-Match nicht ausgewertet gekennzeichnet.
Session-WechselDer aktive Run hält seine Policy bis zum terminalen Loot-/Town-Handoff. Vor dem nächsten Run lädt der Supervisor die aktuelle Assignment-Revision erneut. Ungültigkeit verhindert Start und hält zwischen Runs ohne Gameplay-Input an.
Keine neue Loot-Pipeline: Pickup, Inventarkapazität, Cain, Stash, Akara, Hover-Verifikation und Retry-Budgets bleiben bestehen. Phase 13 ersetzt lediglich die zwei getrennten Dateimatches durch eine einmal kompilierte, aktionsfähige Entscheidungskette und erhält alle Safety-Gates.

7. Dashboard-Bedienung

  1. Profilbibliothek: Name, ID, Regelanzahl, Validität und Verwendungen anzeigen; erstellen, duplizieren, umbenennen und nur unzugeordnet löschen.
  2. Geführte Suche: Freitextsuche über kanonischen Namen, Setname, Basisname und Code. Filter für Sets, Uniques, Basisitems, Gems, Runen, Keys, Qualität und Tier.
  3. Regel hinzufügen: Aktion wählen; bei einem Basisitem optional „Nur ätherisch“. Ein vollständiges Set expandiert vor dem Speichern sichtbar in einzelne Regeln.
  4. Regelliste: Beschriftete Hoch-/Runter-Buttons statt neuer Drag-and-drop-Abhängigkeit, Aktion, deutsche Zusammenfassung, kanonischer Ausdruck, Validitätsstatus und Entfernen.
  5. Fortgeschritten: Das Ausdrucksfeld ist einklappbar, akzeptiert nur den bestehenden Parserumfang plus setitem/uniqueitem und validiert debounced ohne automatische Bedeutungsänderung.
  6. Vorschau: Testitem wählen oder kontrollierte Werte setzen. Jede Regel erscheint als Match/No-Match/übersprungen; das Ergebnis benennt Aktion und Herkunft.
  7. Zuordnungen: Charakter und registrierten Run auswählen, Profile duplikatfrei hinzufügen, sichtbar ordnen und atomisch speichern. Fehlende Zuordnung erklärt, warum der Run blockiert ist.
  8. Unsaved State: Navigation bei Änderungen warnt; Serverantwort ist nach Save autoritativ. „Gespeichert – gilt ab dem nächsten Run“ erscheint nur bei aktiver Session.

8. NIP-Import und -Export

  • Import akzeptiert Paste oder lokalen Dateiinhalt. Der Browser sendet Text; der Go-Core öffnet keinen vom Browser gelieferten Dateipfad.
  • Vor dem Parsen wird genau eine Aktion für alle importierten Regeln gewählt. Gemischte Aktionen erfordern getrennte Importe.
  • Leerzeilen und vorhandene Kommentarformen bleiben erlaubt. Jede aktive Zeile muss vollständig in das dokumentierte Subset passen.
  • Fehler werden gesammelt mit Zeile, Spalte, Ausdruck und Ursache angezeigt. Es gibt keine Teilübernahme und kein stilles Entfernen unbekannter NIP-Sektionen.
  • Import erzeugt lediglich einen UI-Entwurf. Erst normale Validierung und atomisches Speichern erzeugen oder verändern ein Profil.
  • Export dient Portabilität der Ausdrücke. Weil Standard-NIP die Profilaktion nicht verlustfrei trägt, werden Keep- und Sell-Regeln getrennt und mit deutlichen Kommentaren ausgegeben.
  • Koolo-/Kolbot-Kompatibilität wird nicht behauptet. Ein Fremdfile ist nur dann importierbar, wenn jede aktive Regel zufällig vollständig in unserem dokumentierten Subset liegt.

10. Sequenzieller Umsetzungsplan

13.0

Baseline, Verträge und Characterization

  • Aktuellen Parser, First-Match-Verhalten, Pickup-/Keep-/Identify-/Stash-/Sell-Pipeline, Config-Pfade, Run-Preflight, API-Sicherheitsvertrag und React-Struktur mit Characterization-Tests einfrieren.
  • Endgültige YAML-Schemas, Actions, Reason-Codes, Revisionsregeln, Paketgrenzen und Migrationsmatrix dokumentieren, bevor produktiver Code geändert wird.
  • Explizite Non-Goals als Tests/Validierungsfehler festhalten: maxquantity, Sockelalias, Prefix/Suffix und unbekannte NIP-Sektionen.
Gate 13.0 – automatisiert: Bestehende Countess-/Mephisto-Policies liefern vor dem Refactor dieselbe dokumentierte Matchmatrix; Config-, Loot- und Session-Tests sind grün. Plan und Handoff enthalten KISS/YAGNI sowie den verschobenen Socket-Scope.
13.1

Patchgenauer Identitätskatalog

  • Den vorhandenen Itemgenerator minimal um setitems.txt, uniqueitems.txt und item-names.json erweitern oder einen kleinen gemeinsam genutzten Subgenerator hinzufügen; kein zweiter Basisitemkatalog.
  • Pflichtspalten, *ID, String-Schlüssel, Setnamen, Codes, Spawnability, eindeutige IDs/Schlüssel und Referenzen auf den Basisitemkatalog validieren. Abschnittsmarker ohne numerische *ID werden ausdrücklich als Metadatenzeilen übersprungen, nicht als Items oder defekte Stringreferenzen behandelt.
  • Jeden akzeptierten Set-/Unique-Schlüssel eindeutig gegen item-names.json auflösen und enUS als Anzeigenamen generieren; globale doppelte String-Schlüssel außerhalb der tatsächlich referenzierten Itemmenge blockieren den Itemkatalog nicht.
  • Generierten Go-Code mit D2R-Quellversion versehen. Reproduzierbarkeit testen; normale Builds und Tests bleiben unabhängig von .tmp/.
  • Katalogabdeckung für alle fünf Tal-Rasha-Items sowie ausgewählte Unique- und Mehrfach-Amulettfälle fest verdrahten.
Gate 13.1 – automatisiert: Zweimalige Generierung ist byteidentisch; 140 echte Set- und 433 echte Unique-Zeilen sind von Abschnittsmarkern getrennt. Korrupte Header, doppelte relevante IDs/Schlüssel, fehlende englische Anzeigenamen, unbekannte Basiscodes und falsche Quellversionen schlagen vor dem Schreiben fehl.
13.2

Memory-/World-Identität und read-only Live-Beweis

  • Die bekannte Raw-Referenz für Set/Unique am Item-Data-Modell lesen und durch memory.ItemUnit transportieren; Leseprobleme machen nur die Identität unavailable und erzeugen niemals einen geratenen Namen.
  • world.Item um typisierte Identitätsart, Raw-ID, kanonischen Namen und Validitätsgrund ergänzen. Auflösung prüft Qualität und Basiscode gegen den generierten Katalog.
  • Eine read-only Diagnose zeigt bei Inventory-/Ground-Items Code, Qualität, Ethereal, Raw-ID, aufgelösten Namen und Konsistenzstatus. Sie führt keinen Input aus.
Manuelles Gate A – Identitätsprobe: Mit mindestens einem bekannten Set- oder Unique-Item wird live bestätigt, dass Raw-ID, kanonischer Name, Qualität und Basiscode übereinstimmen. Wenn möglich wird zusätzlich ein ätherisches Basisitem geprüft; dessen Fehlen blockiert die Identitätsabnahme nicht. Bei Abweichung stoppt die Umsetzung hier – kein Offset-Raten und kein Katalog-Heftpflaster.
13.3

Minimaler Parser- und Aktionsvertrag

  • [setitem] und [uniqueitem] als einzige neue Felder ergänzen; beide akzeptieren stabile Katalogschlüssel mit ==/!= und werden beim Laden eindeutig aufgelöst.
  • Die vorhandene Quote-Behandlung nur so weit ergänzen, dass der kanonische Serializer Apostrophe, doppelte Anführungszeichen und Backslashes eindeutig roundtrippen kann; keine allgemeine String-Escape-Sprache erfinden.
  • Bestehendes [flag] == ethereal unverändert für Basisitemkombinationen wiederverwenden.
  • Regelmetadaten um stabile Regel-ID, Aktion und Profilherkunft ergänzen; Evaluation liefert einen vollständigen Trace ohne die vorhandene AST-Logik zu duplizieren.
  • First-Match, Re-Evaluation nach Identifikation und fail-closed Identitätsdrift automatisiert abdecken.
Gate 13.3 – automatisiert: Tal-Rasha-Adjudication matcht exakt und ein anderes Set-Amulett nicht; ein ätherischer Thresher matcht, ein nicht ätherischer Thresher und ein anderes ätherisches Basisitem nicht. Alle bisherigen Parserfälle bleiben unverändert grün.
13.4

Profile, Assignments und einmalige Migration

  • YAML-Loader/Writer, Profilservice und Assignment-Store mit Revision, atomischem Replace, Re-Read und Recovery-fähigen Fehlern implementieren.
  • CRUD, Duplizieren, unveränderliche IDs, blockiertes Löschen zugeordneter Profile und duplikatfreie geordnete Assignments implementieren.
  • Bestehende Countess-/Mephisto-Pickup- und Sell-Policies semantisch in initiale Profile migrieren. Die Matchmatrix muss vor/nach Migration gleich bleiben.
  • runs.definitions.*.loot.pickup_file und sell_file nach erfolgreicher Migration aus Schema, Wiring, Beispielen und Tests entfernen; kein Runtime-Fallback und kein toter Loaderpfad.
Gate 13.4 – automatisiert: Crash-/Write-/Revision-/Delete-/Duplicate-Matrix mit Temp-Verzeichnissen besteht. Migrierte Policies reproduzieren Countess und Mephisto exakt; alte Felder werden mit klarer Migrationsmeldung abgelehnt.
13.5

API, Revisionen und sichere Run-Grenze

  • OpenAPI, Go-DTOs, Backend und generierten TypeScript-Client für Katalog, Profile, Validierung, Preview, Assignments, Import und Export ergänzen.
  • Mutationen mit Control-Token, erwarteter Revision, Payload-Limit und bestehenden exklusiven Workflow-Sperren schützen.
  • Session-Preflight um Pickit-Assignment und immutable Policy-Snapshot ergänzen. Eine gespeicherte Änderung wird erst vor dem nächsten Run geladen.
  • Wenn Reload/Validierung scheitert, bleibt der abgeschlossene Run abgeschlossen; der nächste Run startet nicht und die Session wartet fail-closed mit sichtbarem Grund.
Gate 13.5 – automatisiert: API-Vertrag, unautorisierte Mutation, stale Revision, parallele Saves, Save während Run und ungültiger Reload an Run-Grenze sind getestet. Keine Mutation verändert den aktiven Policy-Snapshot.
13.6

React-Profilbibliothek und geführter Editor

  • web/src/features/pickit als eigenes Feature mit Profilbibliothek, Editor, Katalogsuche, Regelreihenfolge, Assignments und Unsaved-State anlegen.
  • Sets/Items/Basisitems verständlich suchen; Setexpansion, Ethereal-Checkbox, zwei Aktionen und deutsche Regelzusammenfassung umsetzen.
  • Fortgeschrittenes Ausdrucksfeld und NIP-Paste/File-Import nur gegen Core-Validierung anbieten. Keine Parserlogik in React nachbauen.

12. Definition of Done

  1. Der Benutzer kann Profile erstellen, duplizieren, umbenennen, ordnen und nur unzugeordnet löschen.
  2. Eine geführte Suche bietet Sets, Einzel-Setitems, Uniques, Basisitems, Gems, Runen, Keys, Qualität und Tier aus generierten patchgenauen Daten an.
  3. „Tal Rasha’s Wrappings“ expandiert deterministisch in fünf explizite Regeln; ein anderes Set-Amulett matcht Tal Rasha’s Adjudication nicht.
  4. Ein konkretes ätherisches Basisitem ist ohne Raw-Code-Kenntnis konfigurierbar und matcht nur Basiscode plus Ethereal-Flag.
  5. YAML-Profile und lokale Assignments sind die einzigen persistenten Autoritäten. Alte Pickup-/Sell-Dateipfade besitzen keinen Fallback.
  6. Mehrere Profile werden pro Charakter/Run duplikatfrei geordnet; das erste Match liefert nachvollziehbar Keep oder Sell.
  7. Fehlende/ungültige Zuordnung blockiert produktive Runs vor Input. Änderungen während eines Runs gelten erst an der nächsten validierten Grenze.
  8. NIP-Paste/File-Import akzeptiert ausschließlich das dokumentierte Subset und arbeitet all-or-nothing; Export behauptet keine vollständige Fremdkompatibilität.
  9. Editorvorschau und Runtime verwenden denselben Go-Parser und dieselbe Katalogauflösung; React enthält keine zweite Entscheidungsengine.
  10. Set-/Unique-Auflösung ist live bewiesen und fail-closed. Unbekannte Identität autorisiert weder Pickup durch eine exakte Regel noch Verkauf.
  11. Pickup, Cain, Stash, Vendor, Inventory-Safety und Input-Verifikation bleiben regressionsfrei.
  12. Godoc, Designkommentare, Feature-Dokumentation, Handoff, Changelog, Dead-Code-Audit, Builds, Lint, Race-Tests und beide manuellen Gates sind abgeschlossen.

D2R Offline Farming Bot · Phase 17

Kampfgesicherte Route durch das Arcane Sanctuary

Phase 17 macht den Summoner-Weg bedrohungsbewusst: Der Bot prüft vor jedem Routenteleport den aktuellen Korridor und den nächsten Landepunkt, hält die Route bei lebenden Gegnern sicher an, räumt ausschließlich bestätigte Arcane-Gegner mit dem Standardangriff des aktiven Kampfprofils auf und setzt exakt denselben Routenfortschritt danach fort. Mana-Burn, Trankverifikation und Drift-Recovery erhalten eigene, endliche Safety-Verträge. Das Ergebnis ist kein allgemeiner Combat-Navigator und keine vollständige Kartenräumung, sondern eine eng begrenzte, testbare Erweiterung der bestehenden Route- und Task-Autoritäten.

Summoner opt-inRoute halten statt verlierenLiving + Hover UnitIDKorridor statt ganze AreaMana-ReserveRejuvenation bei Mana-BurnKeine blinde Drift-KorrekturEndliche BudgetsFail-closed

Vor Gefahr anhalten

Spielerumfeld, aktive Routenkante und nächster Landepunkt werden vor Bewegungsinput gegen den aktuellen Living-Monster-Snapshot geprüft.

Gezielt freikämpfen

Der jeweils nächste relevante Gegner wird pro Snapshot neu bestimmt. Ein Angriff erfolgt nur nach Hover-Bestätigung exakt derselben lebenden Monster-UnitID.

Mana handlungsfähig halten

Teleport startet nur oberhalb einer Reserve. Reine Trankverifikation friert die Route nicht ein; akuter Mana-Burn darf kontrolliert Rejuvenation priorisieren.

Todesloops verhindern

Recovery darf weder denselben wirkungslosen Teleport unbegrenzt wiederholen noch blind zu einem von Gegnern belegten vorherigen Punkt zurückspringen.

TrankverifikationDer Tick mit tatsächlichem Belt-Input verbraucht den Task-Tick. Folgeticks, die nur auf das Verschwinden der Belt-Unit warten, dürfen sichere Combat-/Hold-Logik weiter ausführen und blockieren nicht pauschal die gesamte Route.
Drift-RecoveryVorheriger Punkt oder Korrekturziel werden vor Input durch denselben Threat-Check geschützt. Derselbe effektive Teleport darf ohne bestätigten Positionsfortschritt nicht wiederholt werden.
Erschöpfte BudgetsAnders als Post-Boss-Cleanup wird Route-Combat nicht best-effort übersprungen. Bleibt eine Gefahr nach Cast-/Zeitbudget bestehen, folgt route_threat_clear_exhausted; der Bot teleportiert nicht trotzdem hinein.
Offline-SafetyNur Offline/Singleplayer. Keine D2R-Dateien oder Saves werden verändert. Stop/Pause und Context-Cancellation bleiben an jedem Subzustand wirksam.

5. Exakter Route-Threat-Zustandsautomat

route_moving
  ├─ invalid/loading                      → warten, kein Input
  ├─ low mana                             → route_mana_recovery
  ├─ immediate/corridor/landing threat    → route_clearing
  ├─ safe                                 → genau ein Route.Tick
  └─ route done                           → acquire_boss

route_clearing
  ├─ jeden Tick Route.Hold
  ├─ neues nächstes Living-Ziel           → aim/hover/cast
  ├─ kein Threat für 3 frische Snapshots  → route_moving
  ├─ Mana unter Reserve                   → route_mana_recovery
  ├─ Cast-/Zeitbudget erschöpft           → fail route_threat_clear_exhausted
  └─ Area/Identity/Cancellation falsch     → fail/reset

route_mana_recovery
  ├─ jeden Tick Route.Hold
  ├─ unmittelbarer Threat + kritisches Mana → Rejuvenation-Demand
  ├─ sonst                                 → normale Mana-Demand
  ├─ Mana ≥ Resume-Schwelle                → clearing oder moving neu bewerten
  ├─ kein geeigneter Trank / Timeout        → fail route_mana_recovery_failed
  └─ kein Movement unter Reserve

route_recovery_guard
  ├─ RouteProgress meldet Recovery-Ziel
  ├─ Ziel/Korridor threatened              → clearing
  ├─ identischer Cast ohne Fortschritt     → kein zweiter Blindcast
  ├─ eine sichere Alternative erlaubt      → bounded alternate correction
  └─ weiter kein Fortschritt                → fail route_recovery_unsafe

Die Zustände sind run-generation-scoped und werden bei process_lost, Stop, Run-Ende, Route-Neustart und Step-Wechsel vollständig geleert. Sie werden nicht in Route-YAML oder Telemetrie als Resume-Checkpoint persistiert.

7. RouteProgress- und Hold-Vertrag

type RouteProgress struct {
    RouteID                string
    SegmentID              string
    SegmentIndex           int
    PointIndex             int
    PreviousConfirmed      world.Position
    MovementTarget         world.Position
    TargetAvailable        bool
    Mode                   RouteProgressMode // movement | recovery | transition
    DriftTiles             float64
    LocalRecoveryAttempts  int
}

type RoutePlayback interface {
    Start(routeID string, state world.State) error
    Progress(state world.State) (RouteProgress, bool)
    Hold(state world.State) error
    Tick(context.Context, world.State) (bool, error)
    Reset()
}
  • Progress ist read-only, sendet keinen Input und rekonstruiert nichts aus Telemetrie. Vor Start oder nach Reset liefert es false.
  • PreviousConfirmed und MovementTarget stammen direkt aus RouteSegmentPlayer. Im Recovery-Modus ist MovementTarget das tatsächliche Korrekturziel.
  • Hold validiert Context-unabhängig weiterhin Route, Area, Identität und monotone Snapshotzeit, tickt aber weder Navigator noch TransitionHandler.
  • Der Adapter verschiebt seine aktive Deadline exakt um die seit dem letzten Adapter-Tick vergangene Hold-Dauer. Mehrfacher Hold desselben Snapshots darf keine Zeit doppelt gutschreiben.
  • Hold-Zeit wird separat telemetrisch akkumuliert und besitzt ein eigenes endliches Threat-/Mana-Budget. Sie darf keinen Segmenttimeout umgehen und gleichzeitig unendlich werden.
  • Isoliertes --route play und Guided Validation behalten die bisherige Signatur oder verwenden einen kleinen Adapterpfad, der immer Movement erlaubt. Sie erhalten Phase-17-Combat nicht implizit.

8. Combat-Vertrag während Route-Playback

  1. Bei erkanntem Threat zuerst Route.Hold, danach höchstens eine Combat-Input-Gelegenheit im Tick.
  2. Combat.CastAttackAtMonster bleibt die einzige Angriffsoberfläche: Skillauflösung, Right-Mouse-Gate, Aim, Hover-UnitID und Klick liegen im App-Adapter.
  3. Ein Aim ohne Klick zählt nicht gegen das Cast-Budget. Nur der vom Adapter bestätigte tatsächlich gesendete Rechtsklick erhöht casts_sent.
  4. Nach jedem Klick wird erneut der nächste Living-Threat gewählt. Es gibt keinen mehrsekündigen Route-Pin.
  5. Drei frische, gültige Snapshots ohne relevanten Threat bestätigen stable_clear. Loading/invalid/Area 0 setzen den Clear-Zähler zurück.
  6. Defaultbudget pro Blockade: maximal 20 tatsächliche Angriffe und 12 Sekunden Hold. Beide Grenzen sind konfigurierbar und streng positiv.
  7. Ein Threat außerhalb attack_distance_tiles, der den Landepunkt blockiert, führt nach einem kurzen bestätigten Stabilitätsfenster zu route_threat_out_of_range. Phase 17 erfindet dafür keinen blinden Annäherungsteleport.
  8. Nach Erfolg wird Combat gestoppt, Aim-/Pending-Target zurückgesetzt, RouteProgress frisch gelesen und die Threat-Prüfung erneut durchgeführt. Erst ein weiterhin sicherer Tick darf Route-Movement senden.

Der Post-Boss-Step darf dieselbe kleine pure Auswahlfunktion für „nächstes erlaubtes Living-Monster“ verwenden. Budgets und Abschlussverhalten bleiben getrennt: Post-Boss ist best-effort, Route-Clear ist fail-closed.

Der Profilvertrag wird um einen kleinen ResourceContext erweitert, beispielsweise MobilityCritical, Threatened und EmergencyMana. Die normale Auswahlreihenfolge bleibt außerhalb dieses Kontexts unverändert. Der Resulttyp muss explizit unterscheiden:

profile.Result
├─ Status       complete | pending | action | failed
├─ InputSent    bool
├─ Verifying    bool
├─ Resource
├─ BeltSlot
└─ Reason
  • Runner beendet den aktuellen Tick nur bei InputSent oder Fehler.
  • Verifying ohne neuen Input erlaubt Route-Hold, Threat-Neubewertung und – sofern Mana vorhanden – Combat. Es erlaubt keinen zweiten Belt-Cast.
  • Ein bestätigtes Verschwinden der Belt-Unit bleibt die einzige positive Verbrauchsbestätigung.
  • Die bestehenden Cooldowns bleiben wirksam. Emergency-Kontext darf die Ressourcenart priorisieren, aber keinen Cooldown oder fehlenden Belt-Inhalt vortäuschen.
  • HP-kritische Full-Rejuvenation behält höchste Priorität. Mana-Burn-Rejuvenation ist nur im Summoner-Route-Threat-Kontext aktiv.

10. Drift-, Stuck- und Recovery-Sicherheit

  1. RouteSegmentPlayer exponiert den Modus recovery und dessen tatsächliches Ziel, ändert aber nicht selbst die Combat-Policy.
  2. Vor jedem Recovery-Tick prüft der ThreatController Immediate-, Corridor- und Landing-Zone gegen das Recovery-Ziel.
  3. Ein tatsächlicher Teleport wird durch Zielkoordinate, Startposition, Sendezeit und folgenden Snapshot identifiziert. Ein frischer Snapshot muss mindestens stuck_progress_tiles Fortschritt oder Punktabschluss zeigen.
  4. Ohne Fortschritt darf derselbe effektive Zielpunkt nicht erneut blind gecastet werden. Navigator und RoutePlayer erhalten genau einen klaren „no progress“-Befund.
  5. Optional ist genau eine sichere alternative Korrektur auf der aktiven Routenkante zulässig. Sie muss innerhalb max_drift_tiles, frei von Landing-Threats und näher an der Kante als die aktuelle Position sein.
  6. Ist keine sichere Alternative vorhanden oder bringt sie keinen Fortschritt, endet der Run mit route_recovery_unsafe. Session-Lifecycle kann danach das Spiel kontrolliert verlassen und nach bestehender Retry-Policy neu starten.
  7. max_local_corrections bleibt eine absolute Obergrenze. Route-Combat erhöht sie nie und setzt sie nicht durch Monsterkills zurück.
  8. Ein Threat-Hold zählt nicht als Stuck, weil kein Movement beauftragt ist. Ein gesendeter Combat-Cast zählt umgekehrt nicht als Routefortschritt.
Verbotene Recovery: Kein zufälliger Bildschirmoffset, kein alternierendes „links/rechts“, kein größerer max_drift_tiles-Default und kein dritter Versuch auf denselben gefährlichen Punkt. Sichere Alternative oder klarer Abbruch.

11. Config- und Defaultvertrag

runs:
  definitions:
    summoner:
      combat:
        profile: necro_bone_spear
        attack_skill: bone_spear
        ...
      route_combat:
        enabled: true
        immediate_radius_tiles: 18
        corridor_width_tiles: 7
        landing_radius_tiles: 10
        attack_distance_tiles: 30
        clear_confirm_ticks: 3
        max_casts_per_blocker: 20
        max_clear_duration_ms: 12000
        teleport_mana_reserve_percent: 20
        resume_mana_percent: 35
        emergency_mana_percent: 10
        mana_recovery_timeout_ms: 5000
        max_alternate_corrections: 1
  • enabled muss Presence unterscheiden können. Fehlend bedeutet für Summoner true, für alle anderen Runs false; ein explizites false bleibt möglich.
  • Radien und Angriffsdistanz müssen endlich und positiv sein. corridor_width < immediate_radius < attack_distance und landing_radius < attack_distance.
  • Prozentwerte liegen in 1…100; emergency < reserve ≤ resume.
  • Budgets sind streng positiv und nach oben begrenzt. Empfohlene Maxima: 60 Casts, 30 Sekunden Clear, 15 Sekunden Mana-Recovery, zwei Alternativkorrekturen.
  • enabled: true ist nur bei einer Registry-Definition mit Route-Threat-Capability zulässig. Phase 17 registriert ausschließlich Summoner.
  • NPC-IDs, Skill-ID und Belt-Slots stehen nicht im Route-Combat-Block. Gegner stammen aus der Run-Definition, Skill aus CombatConfig, Ressourcen aus dem Combat-Profil.
  • Keine neue Config-Schema-Version nur für additive Felder. KnownFields bleibt streng; Defaults werden vor Validierung run-ID-bewusst angewendet.

13. Timeout-, Pause-, Stop- und Resetvertrag

  • Jeder Threat-/Mana-Zustand besitzt eigene Startzeit und Zähler. Kein Budget wird aus globalem step_timeout_ms abgeleitet.
  • Route.Hold friert nur die interne Segment-/Transition-Deadline; Threat-/Mana-Budgets laufen weiter.
  • Benutzer-Pause friert wie bisher Task-Ticks und damit alle Phase-17-Budgets. Nach Resume wird zuerst World/RouteProgress neu bewertet, nie sofort der alte Input wiederholt.
  • F11, Context-Cancellation und process_lost rufen Combat.StopAttack, Route.Reset, Profile.Reset und ThreatController.Reset genau einmal über die zentrale Generation-Barriere auf.
  • Areawechsel während Route-Clear oder Mana-Hold ist nur zulässig, wenn RouteProgress bereits in einer erwarteten Transition steht. Arcane-Summoner hat ein terminales Same-Area-Segment; jeder unerwartete Wechsel bleibt fail-closed.
  • Ein invalid/loading Snapshot sendet keinen Input, bestätigt keinen Kill, erhöht keinen stable-clear-Zähler und wiederholt keinen Teleport.
  • Nach erfolgreichem Clear beginnt der nächste Tick mit frischem RouteProgress und neuer Threat-Auswertung. Clear-Abschluss und Teleport liegen niemals im selben Tick.

16. Sequenzieller Umsetzungsplan

17.0

Baseline, Live-Belege und compile-naher Vertrag

  • Aktuellen Stand einschließlich Phase-17-Vorarbeiten nicht verändern, bevor vollständige Go-/Web-/Installer-Baseline und relevante Summoner-/Route-/Profile-Tests grün sind.
  • Die vorhandenen Telemetriebelege für Mana-Burn, play_bound_route, acquire_boss, F11-Abbruch und Route-Drift zeitlich korrelieren. Keine Behauptung „Stuck“ ohne Positions-/Point-/Recovery-Beleg.
  • Die produktive Summoner-Route read-only charakterisieren: Punktabstände, Toleranzen, maximale Abweichungen, Wiederholungen und bekannte gefährliche Abschnitte. Route nicht neu aufnehmen oder still editieren.
  • docs/features/phase-17-core-contract.md mit Entscheidungen, States, Config, Reasons, Budgets, Safety und Non-Goals anlegen.
  • Pure Vertragstypen für RouteProgress, RouteCombatConfig, ThreatZone, RouteThreatState, ResourceContext und Reasons compile-nah definieren.
Gate 17.0: Baseline grün; konkrete Logs belegen die drei getrennten Ursachen Bewegung ohne Threat-Check, blockierende Ressourcenverifikation und gefährliche Recovery; Vertrag und Non-Goals sind vollständig, bevor produktiver Inputcode geändert wird.
17.1

RouteProgress und deadline-sicheres Hold

  • RouteSegmentPlayer um eine read-only Progressprojektion ergänzen, einschließlich Normal-/Recovery-Ziel und PreviousConfirmed.
  • RoutePlayer delegiert Progress ohne Mutation. App-Adapter mappt ihn in die schmale Task-Oberfläche.
  • routePlaybackAdapter.Hold implementieren: Identität/Area/Monotonie prüfen, keinen Navigator tickern und Deadline exakt um echte Hold-Dauer verschieben.
  • Route- und Adaptertests für Point-/Segmentstabilität, Transition, Recovery, identische Snapshots, Deadline und Reset schreiben.
  • Isoliertes Route-Playback und Recording unverändert charakterisieren.
Gate 17.1: Eine Route kann über synthetische 10 Sekunden gehalten werden, ohne Input, Timeout oder Verlust von Segment/Point/Recovery; nach Resume wird exakt der vorherige Fortschritt fortgesetzt.
17.2

Pure Threat-Auswahl und Summoner-Config

  • Run-ID-bewussten Configblock samt Presence-Default und strenger Validierung implementieren.
  • Summoner-Registry um Capability und Arcane-Hostile-Katalog ergänzen; rohe IDs nicht in YAML spiegeln.
  • Pure Geometriefunktionen für Immediate, Landing und vorausliegenden Corridor implementieren; bestehende Distanz-/Segmentmath wiederverwenden oder klein im Task-Paket halten.
  • Deterministische Zielordnung und vollständige Grenzmatrix testen.
  • No-Threat-Summoner-Route durch Characterization-Test byte-/verhaltensgleich halten.
Gate 17.2: Threat-Auswahl ist ohne Input vollständig testbar; entfernter paralleler Arm blockiert nicht; fehlende installierte Config aktiviert nur Summoner; andere Runs verändern sich nicht.
17.3

Route-Clear-State und hover-bestätigter Standardangriff

  • Kleinen generation-scoped RouteThreatController in internal/tasks implementieren.
  • play_bound_route ordnet pro Tick genau eine Aktion an: Hold/Combat oder Route.Tick.
  • Vorhandene Monster-Aim-/Hover-Oberfläche verwenden und Ziel pro Snapshot neu berechnen.
  • Stable-clear, Cast-/Zeitbudget, Range-Gate, StopAttack und Reset implementieren.
  • Post-Boss-Zielauswahl gegebenenfalls in pure gemeinsame Helper extrahieren, ohne dessen best-effort Semantik zu ändern.
Gate 17.3: Ghost am Spieler, im Korridor oder am Landepunkt verhindert jeden Routenteleport; nur exakte Living-/Hover-UnitID wird angegriffen; nach drei freien Snapshots setzt dieselbe Route frühestens im Folgetick fort.
17.4

Mana-Reserve und nichtblockierende Ressourcenverifikation

  • ResourceContext und explizite Resultfelder InputSent/Verifying ergänzen.
  • Runner nur bei tatsächlichem Ressourceninput oder Fehler früh zurückkehren lassen; reine Verifikation erlaubt Threat-/Hold-Fortschritt.
  • Summoner-Route meldet Mobility-/Threat-/Emergency-Kontext. Profil priorisiert HP-kritische Rejuvenation, danach Mana-Burn-Rejuvenation, danach normale Regeln.
  • Route-Mana-Hold mit Reserve, Resume-Hysterese und endlichem Timeout implementieren.
  • Alle Profil-/Runner-/Belt-Tests einschließlich „höchstens ein echter Input pro Tick“ erweitern.
Gate 17.4: Unter Reserve wird kein Teleport gesendet; akuter Mana-Burn kann Rejuvenation nutzen; passives Verify friert die Route nicht 1,5 Sekunden vollständig ein; fehlende Erholung endet schnell und eindeutig statt im Todesstillstand.
17.5

Threat-geschützte Drift- und Stuck-Recovery

  • Recovery-Ziel aus RouteProgress durch denselben Threat-Controller führen.
  • Gesendeten Movement-Cast und folgenden Positionsfortschritt generation-/point-scoped verfolgen.
  • Identischen Teleport ohne Fortschritt unterdrücken; höchstens eine geometrisch sichere Alternative auf der aktiven Kante zulassen.
  • Kein Reset von Route-Correction-Budgets durch Combat. Saubere Reasons und Telemetrie ergänzen.
  • Navigator-/Route-/Task-Integration mit Pack am PreviousPoint und abweichender Landung testen.
Gate 17.5: Kein Testpfad kann mehr als einen wirkungslosen Cast auf dieselbe effektive Zielposition senden; ein bedrohtes Recovery-Ziel löst Clear oder sicheren Abbruch aus, niemals blinde Wiederholung.
17.6

Telemetry, vollständige Regression und Dokumentation

  • Events und stabile Reasons aus Abschnitt 12 ergänzen; Aggregate statt Tick-Flut.
  • Vollständige Go-Matrix, go vet, Lint, Windows-Build und – nur bei tatsächlich neuer Nebenläufigkeit – UCRT64-Race ausführen.
  • Feature-Doc route-threat-combat.md anlegen; Summoner, Route Playback, Task Runner, Encounter Profiles, World Model, README, Changelog und Handoff aktualisieren.
  • Dead-Code-/Invarianten-Audit: keine zweite Hostile-Liste, kein Route-YAML-Reparse in Tasks, kein direkter Input im ThreatController, keine unbegrenzte Recovery.
  • Installer mit neuer Patchversion vollständig bauen und Produkt-Smoke ausführen.
Gate 17.6: Automatische Matrix und Installer-Smoke grün; Dokumentation nennt echte Defaults, Events und Grenzen; Nicht-Summoner-Runs und Diagnoseoberflächen sind unverändert.
17.7

Manuelle Hell-Abnahme und Freigabe

  • Frisch installierten Core und vorhandenen MrBones-Datenroot verwenden; effektive Phase-17-Config vor Start diagnostisch projizieren.
  • Gezielt Runs mit Specter/Ghost, Hell Clan und Ghoul Lord auf der aktiven Route beobachten.
  • Mana-Burn-, Landing-Pack- und Drift-Recovery-Fälle anhand sichtbaren Verhaltens und JSONL-Events abgleichen.
  • Mindestens 20 vollständige Summoner-Hell-Runs oder bis zum ersten Phase-17-Defekt ausführen. Jeder manuelle Eingriff, Tod, Timeout und Restart wird als Nichtbestehen gewertet und mit Run-ID dokumentiert.
  • Erst nach bestandenem Gate Handoff und Phase-Status auf abgeschlossen setzen.
Gate 17.7: 20 aufeinanderfolgende Summoner-Hell-Runs ohne manuellen Abbruch, Route-Todesloop, Teleport in bekannten Landing-Threat, dauerhaften Mana-0-Stillstand oder verlorenen Routefortschritt. Bosskill, Loot, Portal, Act-2-Egress und Act-1-Handoff bleiben erfolgreich.

18. Definition of Done

  • Summoner besitzt als einziger Run ein standardmäßig aktives, explizit deaktivierbares Route-Combat.
  • Vor jedem Routenteleport sind Immediate-, Corridor- und Landing-Threats aus dem aktuellen Living-Snapshot geprüft.
  • Kein Angriff erfolgt ohne exakte Hover-Bestätigung derselben aktuell ausgewählten Monster-UnitID.
  • Route-Hold bewahrt Segment, Point, Recovery und Deadline korrekt und endlich.
  • Unter Mana-Reserve wird kein Teleport gesendet; akuter Mana-Burn besitzt bestätigte Recovery oder schnellen fail-closed Ausgang.
  • Passive Belt-Verifikation blockiert keine inputfreie Threat-/Hold-Verarbeitung.
  • Kein identischer wirkungsloser Recovery-Teleport kann wiederholt in dasselbe Pack gesendet werden.
  • Cast-, Clear-, Mana- und Recovery-Budgets sind endlich, validiert, telemetriert und reset-sicher.
  • Countess, Mephisto, Nihlathak, Post-Boss-Cleanup, Recorder, isoliertes Playback und Town-Egress regressieren nicht.
  • Godoc, Designkommentare, Feature-Dokumentation, README, Changelog und Handoff stimmen mit dem produktiven Verhalten überein.
  • Go-/Web-/Lint-/Windows-/Installer-Gates sind grün.
  • Die manuelle 20-Run-Hell-Abnahme ist ohne Eingriff bestanden und anhand konkreter Run-IDs protokolliert.

20. Bewusste Übergaben nach Phase 17

  • Übertragung des Route-Threat-Combat auf Countess oder andere Runs erst nach eigener Live-Charakterisierung und Registry-Freigabe.
  • Klassen- oder profilspezifische Flächenangriffe, Immunitäten und Skillrotationen bleiben spätere Combat-Profilevolution.
  • Vollständiges Tile-Map-Pathfinding oder dynamische Routenplanung bleibt außerhalb des aufgezeichneten Route-Modells.
  • Automatische Belt-Befüllung aus Inventar sowie wirtschaftliche Trankplanung bleiben Town-/Inventory-Scope.
  • Eine UI für Route-Combat-Tuning wird erst bewertet, wenn mehr als ein produktiver Run oder mehr als ein Profil dieselben Parameter tatsächlich benötigt.

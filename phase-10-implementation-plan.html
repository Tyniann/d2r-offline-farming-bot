D2R Offline Farming Bot · Phase 10

Erweiterbare Run-Definitionen und Mephisto

Phase 10 löst den vollständigen Farming-Lifecycle aus der Countess-spezifischen State-Machine, migriert Countess ohne Verhaltensverlust auf einen gemeinsamen typisierten Run-Vertrag und integriert Act-3-Mephisto als zweites echtes Farmziel. Der erste Mephisto-Scope ist fest an MrBones, Nightmare, Durance-of-Hate-Level-2-Waypoint und eine gültige aufgezeichnete Route gebunden. Automatische Kartenerkundung bleibt ausgeschlossen.

Architekturbeweis

Countess und Mephisto verwenden denselben Session-, Waypoint-, Route-, Encounter-, Loot-, Portal- und Town-Lifecycle. Zielspezifisch bleiben nur Daten und nachweislich notwendige Strategien.

Zweiter Run

Act 1 → Durance Level 2 → aufgezeichnete Route → Mephisto → Loot → Kurast-Docks → Act-1-Hub → Save & Exit.

Loot-Test

Makellose/perfekte Gems bleiben Stash-Loot. Exceptional-/Elite-Set- und Unique-Items werden aufgenommen, bei Cain identifiziert und bei Akara verkauft.

GUI-Vorbereitung

Eine read-only CLI-/JSON-Abfrage liefert Run-Metadaten und Verfügbarkeit. Die lokale API und GUI-Anbindung folgen erst in Phase 11.

4. Gemeinsamer Run-Vertrag

type RunDefinition struct {
    ID                 RunID
    DisplayName        string
    EntryArea          world.AreaID
    RouteTerminalArea  world.AreaID
    WaypointTarget     pathing.WaypointTargetID
    Boss               BossDescriptor
    BossEngageSequence []EncounterAction
    ReturnOrigin       town.OriginAct
    RequiredCaps       []RunCapability
}

type RunConfig struct {
    RouteID string
    Combat  CombatConfig
    Loot    RunLootConfig
}

type RunAvailability struct {
    RunID       RunID
    DisplayName string
    Status      string // available | unavailable | runtime_validation_required
    Reasons     []string
    Route       RouteAvailability
}

Die endgültigen Go-Namen werden in 10.0 festgeschrieben. Wichtig ist die Trennung: Produktidentität und feste Fähigkeiten kommen aus der Registry; operatorabhängige Route, Profil und Tuning kommen aus Config; Live-Layout und UI werden erst durch Preflight beziehungsweise den zuständigen Executor bestätigt.

Spätere Farm-Reihenfolge: Eine GUI soll später beispielsweise mephisto → countess → baal zusammenstellen. Phase 10 implementiert dafür stabile IDs, Metadaten und Verfügbarkeitsgründe. Die Session führt weiterhin genau eine ausgewählte Definition aus; der spätere Scheduler orchestriert mehrere Sessions, ohne Run-Interna zu kennen.

5. Gemeinsame State-Machine

resolve_definition
→ precheck
→ town_ready_profile
→ acquire_act1_waypoint
→ select_run_waypoint
→ wait_entry_area
→ play_bound_route
→ acquire_boss
→ boss_engage_action[0..n]
→ engage_boss
→ confirm_kill
→ scan_and_pick_loot
→ cast_and_enter_town_portal
→ wait_origin_town
→ normalize_to_act1_hub
→ stash_and_services
→ reach_act1_waypoint
→ complete
  • Jeder Zustand besitzt erlaubte Vorgänger, zulässige World-Areas, Input-/Verify-Budget, Timeout und stabilen terminalen Reason-Code.
  • Persistenter Zustand über Ticks: Definition, Route-/Layout-Bindung, gepinnte Boss-UnitID, Encounter-Aktionsindex, Loot-Skips, Town-Plan und Telemetrie-Recorder.
  • Reset verwirft alle Pins, Once-/Settle-Zustände, laufende Player/Executor und Recorder-Bindungen. Es darf kein verzögerter Input in den nächsten Run gelangen.
  • Countess und Mephisto verwenden dieselbe Transition-Tabelle. Unterschiedliche Aktionsanzahl, Areas und IDs werden ausschließlich aus der Definition gelesen.
  • Loading-/inkonsistente Snapshots dürfen innerhalb der explizit erlaubten Übergangszustände warten; in jedem anderen Zustand gilt fail-closed.

7. Umsetzungsabschnitte

10.0

Vertrag, Characterization und Refactor-Grenzen

Den gemeinsamen Run-Vertrag, Capabilities, Zustände, Übergänge, Reset-Grenzen, Availability-Status und Reason-Codes verbindlich festlegen. Vor Umbauten werden Characterization-Tests für den aktuellen Countess-Full-Run, Session-Preflight, Route-Bindung, Boss-Hook, Loot-Abschluss, Town-Handoff und Save & Exit ergänzt. Alle Countess-spezifischen Kopplungspunkte werden in einer Migrationsmatrix einem gemeinsamen Baustein oder zulässigen Definitionsfeld zugeordnet.

  • Kein Produktivverhalten ändern.
  • Invarianten und fail-closed Entscheidungen gemäß AGENTS.md direkt am kleinsten hilfreichen Code-Scope dokumentieren.
  • Explizit festhalten, welcher Altcode nach der Migration entfernt werden muss.

Gate 10.0: Alle bestehenden Tests sowie neue Characterization-Tests laufen grün; die Migrationsmatrix enthält keinen ungeklärten Countess-Sonderpfad. go test ./... und go build ./cmd/d2rbot erfolgreich. Kein manueller Test.

10.1

Run Registry, gemeinsames Config-Schema und Definition Resolver

RunDefinition, RunRegistry und ein einheitliches RunConfig-Schema implementieren. Countess wird als erste registrierte Definition abgebildet; Mephisto darf zunächst nur Metadaten ohne produktive Ausführung besitzen. runs.countess-Sonderzugriffe werden durch ID-basierte Auflösung ersetzt. Run-spezifische Pickup-/Sell-Policy-Dateien gehören zur ausgewählten Config, globale Loot-Engine und Inventory-Lock bleiben gemeinsam.

runs:
  active: ""
  step_timeout_ms: 30000
  definitions:
    countess:
      route_id: "..."
      combat: { profile: necro_bone_spear, attack_skill: bone_spear, ... }
      loot: { pickup_file: pickit/countess.nip }
    mephisto:
      route_id: ""
      combat: { profile: necro_bone_spear, attack_skill: bone_spear, ... }
      loot:
        pickup_file: pickit/mephisto.nip
        sell_file: pickit/mephisto-sell.nip

Die endgültige YAML-Struktur darf kompakter sein, muss aber für beide IDs exakt denselben Typ laden. Da das Projekt keine Legacy-Kompatibilität verlangt, wird das alte Countess-Sonderschema vollständig migriert und nicht parallel weitergeführt.

Gate 10.1: Tests decken doppelte/ungültige IDs, fehlende Config, unbekannte Run-Auswahl, ungültige Capability-Kombinationen, getrennte Loot-Dateien und identische Countess-Defaults ab. Repository-Suche findet außerhalb von Definition, Tests und Dokumentation keinen direkten Zugriff mehr auf cfg.Runs.Countess. Kein manueller Test.

10.2

Gemeinsame Run-Pipeline und vollständige Countess-Migration

Die monolithische Countess-State-Machine in eine datengetriebene, aber typisierte Pipeline überführen. Waypoint-Reise, Routen-Playback, Boss-Pinning, Encounter-Aktionssequenz, Combat, Loot, Portal, Town und Abschluss werden gemeinsame Steps. Countess liefert ausschließlich Definition und Config. Bestehende isolierte Phasen werden entweder generisch benannt oder über einen dünnen, dokumentierten CLI-Alias auf gemeinsame Steps abgebildet.

  • Ein Encounter-Aktionsindex erlaubt Countess genau eine Hook-Aktion und später Mephisto zwei.
  • Boss-Pin, Route-Player, Profile-Executor, Loot-Executor und Town-Executor werden an einer zentralen Reset-Barriere geleert.
  • Alte Countess-Step-Switches, doppelte Prechecks und unbenutzte Adapter unmittelbar entfernen; kein toter Fallback-Code.
  • Telemetry behält stabile Run-/Step-/Outcome-Felder und ergänzt Definition-ID sowie Aktionsindex.

Gate 10.2: Die Characterization-Suite aus 10.0 läuft unverändert gegen die gemeinsame Pipeline. Transition-, Timeout-, Reset-, Stop-, Pause- und Telemetriefehler-Tests beweisen keine doppelten Inputs und keinen Zustandstransfer zwischen Runs. Kein manueller Test.

10.3

Generischer Session-Preflight und read-only Run-Verfügbarkeit

ResolveSessionPlan wird von Countess entkoppelt und fragt ausschließlich Registry, ausgewählte Config, Profil, Route Registry und Town-Capabilities ab. Eine neue read-only CLI-Ausgabe, beispielsweise --runs-inspect, listet JSON-stabil alle Run-Metadaten und deren Status für Character, Difficulty und aktuelle Game Identity.

  • available: statische Definition, Config, Profil und passend gebundener Route-Kandidat sind vorhanden.
  • runtime_validation_required: Vorbedingungen passen, der exakte Zielgebiets-Fingerprint kann aber erst nach Ankunft validiert werden.
  • unavailable: mindestens ein stabiler Sperrgrund wie route_missing, route_binding_mismatch, profile_class_mismatch, waypoint_target_unsupported oder town_egress_missing.
  • Die Abfrage registriert keine Hotkeys, sendet keinen Input und startet keine Session.

Gate 10.3: Golden-/JSON-Tests beweisen deterministische Reihenfolge und stabile Reason-Codes. Countess wird für die gültige lokale Bindung verfügbar, Mephisto bleibt bis zur Aufnahme nachvollziehbar gesperrt. Session-Start mit gesperrtem Run endet vor Runtime-Input. Kein manueller Inputtest.

10.4

Countess-Regressionsabnahme nach dem Refactor

Erst nach vollständigem Abschluss von 10.0–10.3 wird der migrierte Countess-Run einmal autonom auf MrBones/Nightmare ausgeführt. Geprüft werden Definition-Auflösung, Session-Preflight, Town-Waypoint, bestehende Route, genau ein Bone Prison, Bone Spear, Loot, Portal, Stash/Restock, Waypoint-Handoff, Save & Exit und Sessionabschluss.

Manuelle Abnahme 1/4: Ein vollständiger telemetrierter Countess-Run endet mit outcome=success, genau einem Boss-Hook und genau einem Save-&-Exit. Keine Countess-Regression und keine Aktivierung von Mephisto-Sondercode. Bei Fehlschlag wird 10.2/10.3 korrigiert und dieses Gate wiederholt; 10.5 beginnt erst nach Erfolg.

10.5

Versionsgebundene Mephisto- und Item-Tier-Daten

Die eigenen Generatoren so erweitern, dass monstats.txt Mephisto über *hcIdx=242 in Memory- und World-Kataloge übernimmt. armor.txt und weapons.txt liefern aus ihren Normal-/Exceptional-/Elite-Verknüpfungen eine generierte BaseTier-Klassifikation. Durance Level 2/3 erhalten die für Route und Transition nötigen semantischen Area-/Entrance-Kinds.

  • Keine handgeschriebene Kopie großer Tabellen.
  • Generatoren validieren Pflichtspalten, Zyklen, unbekannte Referenzen und Game-Version.
  • Der Pickit-Ausdruck erhält einen klaren read-only Tier-Prädikatszugriff, ohne bestehende Countess-Regeln zu verändern.
  • Unbekannte oder nicht aus Waffen/Rüstung stammende Codes besitzen unknown, niemals heuristisch elite.

Gate 10.5: Generator-Fixtures und Katalogtests bestätigen Mephisto 242 sowie bekannte Normal→Exceptional→Elite-Ketten aus Waffen und Rüstung. Negative Tests verwerfen defekte Tabellen. Alle generierten Dateien sind reproduzierbar und go generate/Generator-Check erzeugt keinen unerklärten Diff. Kein manueller Test.

10.6

Run-spezifische Loot-Policies und produktiver Identify-/Sell-Flow

Pickup- und Sell-Filter werden getrennt ausgewertet. mephisto.nip nimmt die bestehenden makellosen/perfekten Gems einschließlich Schädel sowie Exceptional-/Elite-Set/Unique auf. mephisto-sell.nip klassifiziert ausschließlich letztere als Sell-Kandidaten. Gems bleiben Keep/Stash; normale Set-/Unique-Basen werden ignoriert.

Der in Phase 9 vorbereitete ItemServiceExecutor wird produktiv in Demand, Graphplanung und App-Input verdrahtet: ein unidentifizierter Sell-Kandidat geht zu Cain, wird anhand derselben UnitID als identifiziert bestätigt und danach bei Akara verkauft. Identifizierte Sell-Kandidaten überspringen Cain. Konflikte mit Keep/Stash/Inventory-Lock stoppen vor Input. Akara-Restock darf bei ohnehin geöffnetem Shop geordnet kombiniert werden; jedes UI wird vor Navigation bestätigt geschlossen.

Automatisches Gate 10.6: Tests decken alle Quality×Tier×Identified-Kombinationen, Gem-Schutz, UnitID-Pinning, Cain→Akara-Reihenfolge, Shop-Close, fehlenden Kandidaten, Konflikte und Verify-Timeout ohne Doppelinput ab.

Manuelle Abnahme 2/4: Mit genau einem vorbereiteten, unidentifizierten Exceptional-/Elite-Set- oder Unique-Item im ungeschützten Inventar führt ein isolierter Town-Test Cain-Identifikation und anschließenden Akara-Verkauf aus. Ein vorhandener Gem-/Keep-Gegenstand bleibt unangetastet. Dieses Gate ist unabhängig vom Zufall eines Mephisto-Drops.

10.7

Generische Waypoint-Ziele und sichere UI-Auswahl

SelectBlackMarsh wird durch eine registrierte SelectWaypointTarget-Aktion ersetzt. Registriert werden Black Marsh, Durance of Hate Level 2 und Rogue Encampment. Jede Aktion beschreibt erforderlichen Akt-Tab, Zielzeile, Auflösungsbindung, Settle und erwartete Ziel-Area; UI-Eingaben erfolgen nur nach bestätigtem Waypoint-UI-Zustand und höchstens einmal pro Tick.

  • Black-Marsh-Koordinaten werden migriert, nicht dupliziert.
  • Durance Level 2 erfordert bestätigten Act-3-Tab und danach die registrierte Zeile.
  • Rogue Encampment wird für den Transfer aus Kurast-Docks registriert.
  • Nach Auswahl wartet der Step auf die erwartete Area; falsche Area oder Timeout wiederholt keinen Klick.

Gate 10.7: Unit-/Adaptertests decken Act-Tab, Zielzeile, Settle, falsche Auflösung, unbekanntes Ziel, falsche Area, Timeout und Reset ab. Eine read-only/isolierte Kalibrierung liefert die finalen 1280×720-Koordinaten; echter Travel-Input wird mit dem kombinierten Gate 10.9 abgenommen.

10.8

Act-3-Egress und Hub-Transfer

Kurast-Docks werden als produktiver OriginAct3-Rückkehrzustand integriert. Das vorhandene Egress-Schema wird mit einer echten, gebundenen Aufnahme portal_arrival → waypoint gefüllt. Playback bestätigt Area, World-/Identity-Bindung, Startnähe und Waypoint-Ankunft. Danach wählt der gemeinsame Waypoint-Executor Rogue Encampment; Town-Dienste beginnen erst nach bestätigter Act-1-Ankunft.

  • Vor Aufnahme liefert ein read-only Inspect die stabilen Kurast-Anker und entscheidet anhand realer Daten, ob ein Layout-Fingerprint beziehungsweise eine Character-/Difficulty-Bindung erforderlich ist.
  • Kein vollständiger Act-3-Servicegraph.
  • Fehlende Egress-Route, falscher Startanker oder Binding-Mismatch stoppen vor Bewegung.
  • Portalrückkehr, Egress-Player und Waypoint-Transfer besitzen getrennte Reset-/Timeout-Budgets.

Gate 10.8: Automatisierte Route-/Planner-Tests beweisen Kurast-Docks → Waypoint → Rogue Encampment und alle negativen Bindungsfälle. Aufnahme und echter Playback werden in Gate 10.9 mit der Mephisto-Route gebündelt.

10.9

Mephisto-Routenaufnahme und kombinierte Navigationsabnahme

Mit dem bestehenden Recorder wird auf MrBones/Nightmare eine vollständige Route vom Durance-Level-2-Waypoint über den Übergang nach Level 3 bis zu einer reproduzierbaren Bone-Spear-Kampfposition aufgezeichnet. Die Route trägt Character, Class, Difficulty, Game-Version, Map-Seed, Layout-Fingerprint, Start-/Ziel-Areas und Segmentübergänge. Zusätzlich wird der Act-3-Egress aus 10.8 aufgenommen.

  1. Vor Aufnahme zeigt --runs-inspect Mephisto als route_missing.
  2. Durance-Route und Kurast-Egress separat aufnehmen und strukturell validieren.
  3. Keine Punkte manuell kürzen oder aus Konsolenausgabe rekonstruieren; die persistierte Datei ist autoritativ.
  4. Kombinierter Test: Act-1-Waypoint → Durance Level 2 → Durance-Route bis Kampfposition; ohne Kampf anschließend separat Kurast-Portalankunft → Waypoint → Rogue Encampment.
  5. Danach zeigt der Resolver einen passenden Route-Kandidaten beziehungsweise den präzisen Status runtime_validation_required.

Manuelle Abnahme 3/4: Beide Aufnahmen spielen vollständig ohne Drift, Abkürzung oder halben Segmentabbruch ab. Durance Level 3 und Rogue Encampment werden jeweils per Memory bestätigt. Der CLI-Resolver wechselt nachvollziehbar von fehlender Route zu verfügbarer/Runtime-Validierung. Erst danach beginnt die Bossintegration.

10.10

Mephisto-Definition, doppeltes Bone Prison und Loot-Abschluss

Die Mephisto-Definition wird produktiv freigeschaltet: Durance-Level-2-Waypoint, aufgezeichnete Route, Terminalarea Level 3, NPC-ID 242, zweimalige boss_engage-Aktion und Bone-Spear-Combat. Beide Bone-Prison-Aktionen verwenden dieselbe gepinnte Mephisto-UnitID, besitzen getrennte Aktionsindizes und Settle-Phasen; der erste Bone-Spear-Cast ist vorher gesperrt.

  • Mephisto-Verlust, UnitID-Wechsel oder Tod vor Abschluss der Sequenz stoppt fail-closed.
  • Kill-Bestätigung verwendet mehrere konsistente Ticks und nicht nur das Verschwinden aus einem Snapshot.
  • Loot nutzt die Run-spezifischen Policies aus 10.6.
  • Bei Inventory Full endet der Scan und wechselt zum Town-Pfad; kein Rückkehrportal zum Restloot.
  • Nach Loot wird ausschließlich das eigene, hover-bestätigte Town Portal betreten und Kurast-Docks erwartet.

Gate 10.10: State-Machine-/Integrationstests beweisen exakt zwei Bone Prisons, Reihenfolge und Settle vor Bone Spear, Kill-Confirm, zufälligen No-Drop, passenden Sell-Loot, Inventory Full, Portal und erwartete Act-3-Ankunft. Countess-Tests beweisen weiterhin exakt einen Bone-Prison-Cast. Kein separater Söldnertest.

10.11

Vollständige Session-Integration, Telemetrie und Abschluss

session.run=mephisto verwendet denselben Start-/Exit-/Restart-Lifecycle wie Countess. Der produktive Flow verbindet Definition-Resolver, Waypoint, Route, Encounter, Loot, Kurast-Egress, Act-1-Hub, Stash, optionale Cain-/Akara-Dienste, Waypoint-Handoff und genau ein Save & Exit. Fehlende Loot-Drops überspringen Identify/Sell ohne künstlichen Fehler.

Telemetrie enthält Run-ID, Definition, Route-Bindung/Fingerprint, Waypoint-Ziel, Boss-UnitID, Encounter-Aktionsindex, Loot-Policy/Disposition, Town-Origin, Serviceplan und terminalen Reason-Code. Session-Retry bleibt an bestehende klassifizierte Fehler gebunden; Binding-/Capability-Fehler sind nicht retrybar.

Manuelle Abnahme 4/4: Ein autonomer mephisto-Run auf MrBones/Nightmare startet im Rogue Encampment, erreicht Durance Level 2/3, castet exakt zweimal Bone Prison vor Bone Spear, bestätigt Mephistos Tod, verarbeitet Loot, kehrt über Kurast-Docks und den Act-3-Egress nach Act 1 zurück und endet nach Town-Preparation mit genau einem Save & Exit und outcome=success. Cain/Akara sind in diesem Zufallsrun nur erforderlich, wenn passender Sell-Loot fällt; ihre produktive Funktion ist bereits deterministisch in Gate 10.6 bewiesen.

10. Definition of Done

  1. Countess und Mephisto sind registrierte Definitionen desselben typisierten Schemas.
  2. Beide Runs verwenden denselben Session-Preflight, Lifecycle, Reset, Telemetrie- und Input-Wiring-Pfad.
  3. Es existiert kein produktiver Countess-only Session- oder Waypoint-Sonderpfad mehr.
  4. --runs-inspect oder das endgültig benannte Äquivalent liefert stabile JSON-Metadaten und Verfügbarkeitsgründe ohne Input.
  5. Mephisto bleibt ohne gültige MrBones-/Nightmare-/Version-/Map-gebundene Route vor Input gesperrt.
  6. Durance-Level-2-Waypoint, Durance-Route und Kurast-Egress wurden live aufgenommen und vollständig abgespielt.
  7. Mephisto erhält genau zwei Bone Prisons; Countess weiterhin genau eines; Bone Spear beginnt jeweils erst nach dem Encounter-Settle.
  8. Makellose/perfekte Gems werden wie bei Countess verstaut; Exceptional-/Elite-Set/Unique werden sicher identifiziert und verkauft.
  9. Inventory Full beendet den Loot-Scope sauber ohne Rückkehr zum Bodenloot.
  10. Act-3-Rückkehr normalisiert über den Kurast-Waypoint in den Act-1-Hub.
  11. Countess-Regression und Mephisto-E2E enden jeweils autonom mit genau einem Save & Exit.
  12. Alle automatischen Gates, vier manuellen Gates, Dokumentation, Dead-Code-Audit, Build und Lint sind abgeschlossen.

11. Erwartetes Ergebnis für Phase 11

Phase 11 kann über einen stabilen Core-Vertrag Run-Metadaten und Availability lesen, eine einzelne Run-ID für eine Session auswählen und Status/Reason-Codes anzeigen. Die GUI muss weder Countess-/Mephisto-Structs noch Route-Dateiformate kennen. Farm-Reihenfolgen wie mephisto → countess → baal, API-Endpunkte und GUI-Warnungen werden dort auf dem Phase-10-Resolver aufgebaut, nicht in Phase 10 vorweggenommen.
